# 양법인(동산기획·선명) 통장·카드 기반 고정비/지출 관리 — spec

> 작성 2026-08-10. 목표: **두 법인의 "매월 어디에 얼마 나가는가"를 통장내역+카드내역 한 축으로 관리.**
> 기존 자산(fixed_expenses·자동매칭·recurring-candidates·card_transactions) 위에 얹는다. 신규 시스템을 만들지 않는다.

| 통장 거래 | 12계좌 4,957건 (2026-01~08) | 3계좌 872건 (2026-01~08) |

**발견된 구멍 (P1의 근거)**
- ⚠️ **e1 미등록 카드 4장+**: 전북은행(JB) 카드 3장(끝 7988·7996·9243, 매월 22일 결제, 월 74만~1,282만)
  + NH농협카드(매월 15일, 월 40만~152만)가 통장에서 매월 결제되는데 `corporate_cards` 에 없다
  → 사용내역 수집이 안 되고 지출 분석에서 "카드대금 출금 한 덩어리"로만 보인다.
- ⚠️ **e2 하나카드 결제일 오등록 의심**: 등록 pay15 · 실측 출금 매월 10일(01/12·02/10·03/10·04/10·05/11·06/10·07/10 — 주말 보정 포함 일관).
  결제예정 타임라인·자금예측이 5일 어긋난다. (e1 BC·하나 pay15, e2 BC pay10은 실측 일치)
- 카드 수집이 2026-03~04월부터라 1~3월 카드 지출은 통장 덩어리로만 존재.

## 1. 원칙 (기존 결정 승계 — 완화 금지)

- **이중계상 차단이 제1원칙.** 지출은 두 층으로 잡힌다 — ①통장의 「카드대금 출금」(현금 유출 시점) ②카드 사용내역(소비 내용).
  **금액 집계는 한 층에서만**: 현금흐름은 ①, 지출 성격 분석은 ②. 둘을 더하면 카드 지출이 2배가 된다.
  같은 원리의 기존 사례 = 리스료(차입금+고정비+감가상각 삼중계상 → memory `design-loan-liability-model`).
- **자동매칭은 정밀도 우선** — 규칙 완화 금지 (memory `project-bank-fund-expansion` 2026-07-27 오매칭 사고).
- **고정비 신규 등록은 세무장부 계정 확인 후** — 저축·자산성 지출이 비용으로 섞이는 걸 막는 유일한 장치 (memory `feedback-recurring-expense-detection`).
- **사용량 변동(전기·수도)은 ESTIMATED 트랙**, 급여 연동은 고정비 제외.
- 법인 분리는 기존 entityFilter 체계 그대로 (통장·카드·고정비 모두 entity_id 보유). 신규 축 불요.

## 2. 단계

### P1 — 데이터 완결성 (선행, 코드 거의 없음)
1. **미등록 카드 등록**: e1 전북은행 3장·NH농협 1장을 `corporate_cards` 에 등록하고 바로빌 수집 연동.
   - 검토 확인(2026-08-10): **바로빌 카드수집은 전북(JBBANK)·NH 지원** (`barobillCodes.ts`). 단 카드사 셀렉트·`BAROBILL_CARD_COMPANY_CODES` 에 '전북' 이 빠져 있어 추가 필요.
   - **연동에는 카드사 홈페이지 ID/PW 가 필요**(1회 전송·미저장) → 등록은 먼저 수동(미연동)으로 하고, 연동은 [카드 관리]에서 인증정보 입력으로.
   - ⚠️ NH농협은 매월 15일 본출금 + 다음날 소액 2차 출금 패턴(01·05·06월) — **카드 2장일 가능성**, 명세서로 확인.
2. **결제일 정정**: e2 하나카드 3장 pay15→10. 실출금 7개월 연속 10일(주말보정 일관)이라 결제일은 통장이 근거로 충분. **마감일(cutoff)은 명세서 확인 전까지 유지.**
3. **e2 고정비 보강**: `/api/bank/recurring-candidates` 를 선명 법인으로 실행해 후보 검토
   (e1 은 2026-08-05 에 이 방법으로 월 1,587만 발굴 — e2 는 같은 스윕을 한 적이 없다). `bank_transactions.entity_id` 존재 확인됨 — entity 전환만으로 동작.
4. 선명 세무장부(WEHAGO)로 후보 성격 확정 → 고정비 등록. **차입금·리스는 loans/고정자산과 겹침 확인 후 등록.**

### P2 — 카드 지출을 분류 체계로 흡수
- 문제: 통장 지출은 `expense_categories`(bank 매칭)로, 카드 지출은 `card_transactions.category_id`(같은 테이블 — 0270 FK 로 확인됨 — 이지만 별도 화면)로 따로 논다.
  월별 "복리후생비 총액" 같은 질문에 답하려면 둘을 합산해야 하는데 지금은 화면이 없다.
- 설계:
  - 통장의 카드대금 출금(비씨카드출금·하나카드기업·JB카드결제 등)을 **「카드결제 대금」 태그로 자동매칭**(EXACT/CONTAINS 규칙 등록)
    → 지출 성격 분석에서 이 태그는 **제외**하고 card_transactions 분류로 대체(이중계상 차단).
  - 카드 미분류(UNCLASSIFIED) 잔량을 줄이는 운영 루프: 가맹점명 → 분류 규칙 학습(기존 bank_match_rules 패턴 재사용, 카드판 신설).
- 산출물: 월별 × 법인 × 분류 지출 집계 API (`GET /api/expenses/monthly-summary?entity=&period=`)
  = 통장(카드대금 제외) + 카드(분류별) + 고정비 실적(recurring_expense_actuals).

### P3 — 월별 지출 리포트 화면
- 위치: **/bank 신규 탭 「지출 리포트」** (흡수-탭 패턴, 신규 페이지 아님 → 권한 등록 불요).
- 내용:
  - 월별 추이 12개월: 고정비 / 변동(통장) / 카드 / 대출 원리금 4계열 스택.
  - 법인 전환은 기존 entity 스위처 그대로, 「전사 합산」 모드 추가(ADMIN).
  - 분류별 상세 drill-down + 전월비 ±30% 급변 하이라이트.
  - 당월 고정비 체크리스트(기존 P2 기능)와 나란히.
- 주의: **기간 일부만 걸친 고정비를 전 기간으로 곱하지 말 것** (departments.ts 전례 — 월별 중첩만 합산).

### P4 — 예산·이상 탐지 (옵션, P3 실사용 후)
- 분류별 월 예산(settings 키) + 초과 시 대시보드 배지.
- recurring-candidates 정기 스윕(분기 1회) 리마인더 — 미등록 반복지출이 조용히 쌓이는 구조 대응.

## 3. 하지 않는 것
- 카드매출(입금) 쪽은 범위 밖 — 기존 카드매출 정산 매칭 유지.
- 승인내역 실시간 수집(CODEF 등) 신규 연동 — 바로빌 수집 주기로 충분.
- 세무장부 자동 스크래핑 — 성격 확정은 사람이 한다.

## 4. 검증 기준
- P1 후: e1 카드대금 통장 출금 합 ≈ 등록 카드 청구 합(월별, ±수수료), e2 결제예정 타임라인이 실출금일과 일치.
- P2 후: (통장 지출 − 카드대금 태그) + 카드 지출 = 월 총지출이 통장 순유출과 대사.
- P3 후: 임의 월 1개를 세무장부 판관비와 대조(계정 grain 차이는 허용, 방향성 일치 확인).
