## 결정과 이유

- **입고 목적지 = 게이트와 같은 SQL 한 문장**(`zoneByInventorySql`). 09-08 에 담당 게이트에만 재고행 단계를
  넣어서 **게이트만 열리고 목적지는 축1(`items.storage_zone_id`)에 머물러** 있었다. 그 상태로 배정하면
  재고가 전부 **법인 기본창고(동산=출력실)** 로 가고 그 구역 실사표에 안 뜬다. 선명2 는 기본창고라 우연히 맞아
  **테스트해도 티가 안 난다**. 정렬은 `resolveDeductionZone` 과 맞췄다 — 갈리면 입고는 A, 차감은 B 가 되어
  한 구역이 조용히 음수가 된다.
- **`base_price` 는 고객 노출 단가다**(`sales_price` 는 prod 전량 0, priceSheets 09-03 통일). 입고가 이걸
  매입가로 덮고 있었고, 판매품목 367종 중 **135종이 10%+ 이동·115종 하락**(대부분 −40% = 매입÷0.6).
  판매품목은 보존하고 매입가는 `client_item_prices` 에 계속 기록한다.
- **`avg_unit_cost` 는 「0일 때만 채운다」**. 이동평균은 누적 캐시라 취소가 되돌려야 하는데 역산이 순서 의존이다.
  `avg <= 0` 은 자기교정이라 되돌릴 짝이 필요 없다. 정밀 이동평균이 필요하면 그때 **원장 기반 파생**으로.
- **판정은 전부 순수 함수 + 픽스처 게이트**로 뺐다. 세 결함 모두 응답 200 이고 타입체크·빌드·smoke 를
  전부 통과한다 — 값 대조 게이트에서만 잡힌다.

## 판단 기준 (다음에 같은 판단을 할 때)

- **「지금 안 터진다」와 「구조가 안전하다」는 다르다.** 세 결함 다 데이터가 비어서 안 터지고 있었다 —
  입고가 prod 에서 **한 번도 안 돌았고**(`inventory_receipts` 0행) 그래서 3년 잠복했다.
- **적용 전에 prod 로 영향 건수를 센다.** 두 축 변경 모두 「변경 0건」을 확인하고 올렸다. 0건이면
  지금 동작을 안 바꾸면서 앞으로 것만 받아내는 변경이라 되돌릴 일이 없다.
- **공유 지점을 고치면 그 지점을 지나는 경로를 전부 열거한다.** 원장 `IN` 을 쓰는 곳이 발주 입고·수기 입고
  **둘**이라 양쪽에 넣었다. 한쪽만 하면 다른 쪽은 조용히 빈다.

## 주의사항

- ⚠️**SQLite 는 서브쿼리의 ORDER BY 에서 바깥 컬럼을 못 읽는다**(`no such column: i.storage_zone_id`).
  WHERE 는 되고 ORDER BY 는 안 되며 중첩 스칼라 서브쿼리로 감싸도 같다. → 서브쿼리 안에서 `items` 재조인.
  자체검증이 이걸 잡았다. **타입체크·빌드는 SQL 오류를 못 잡는다** — prod D1 에 실제 SQL 을 던져 확인할 것.
- ⚠️`items` 에는 `entity_id` 가 없다. `base_price`·`avg_unit_cost`·`storage_zone_id` 는 전부 **법인 공유**다.
  `recalculate-avg` 가 법인별 집계로 전역 칸을 쓰고 있었다(동산에서 눌러 선명 원가를 바꿈).
- ⚠️**발주 라인 구역 축(`poi.storage_zone_id`)은 죽어 있다** — prod 0건이고 INSERT 문에 컬럼이 없다.
  「라인마다 구역 지정」을 전제로 설계하지 말 것.
- ⚠️소모량은 **같은 품목을 2회 이상** 세야 나오고, **제출(SUBMITTED)** 부터 집계된다(승인은 재고 보정용).
- ⚠️매입 세금계산서(`purchaseInvoices.ts:178`)가 원장 단가를 정정해도 이미 채워진 `avg_unit_cost` 는
  안 따라간다. 채우기 규칙상 첫 입고가가 남는다.
- ⛔**9월 이관(선명·동산·청주) 금지** — 제안도 질문도 하지 않는다.
