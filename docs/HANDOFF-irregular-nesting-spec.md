# HANDOFF — 이형(true-shape) 네스팅 spec 작성

> 작성 2026-07-30 · 목적 = **다음 세션이 spec 문서를 쓸 수 있게 하는 준비**. 이 문서는 spec이 아니다.
> 산출물 = `docs/superpowers/specs/2026-XX-XX-irregular-nesting.md` (brainstorming 스킬 선행 — 신규 기능)

## 1. 한 줄 정의

지금 자동 네스팅은 조각을 **사각형(바운딩박스)** 으로만 취급한다. 삼각형·곡선 조각 사이 빈 공간이 자재 낭비로 남는다. 이형 네스팅 = **조각의 실제 외곽선**으로 맞물리게 배치하는 것.

## 2. 현재 상태 (실측 · 2026-07-30)

| 구분 | 현황 | 근거 |
|---|---|---|
| 자동 패킹 | **bbox 전용** · 패커 정본 = `iaeMaxRectsPack`(maxrects 고정) | `src/scripts/iaEditor.js:943`·`:952` |
| 이형 대응 | **수동 인터록이 prod 라이브** — 사용자가 드래그로 bbox를 겹쳐 끼우고 90° 스냅 회전 | `src/scripts/iaEditor.js:1076~` |
| 시트 멤버십 | 조각 bbox **중심점**의 시트 포함관계(드래그 인/아웃·복제 대응) | `iaeCanSheetForPoint`·`iaeCanReassignSheets`(`:2195`) |

| 검증 게이트 | `node scripts/nesting-harness.mjs` (R1~R5 하드·W1 경고) | `scripts/nesting-harness.mjs` |

**사용 설명서는 이미 있다**: `docs/IA_EDITOR_USAGE.md` §4 "이형(true-shape) 수동 인터록".

### ✅ 해소됨 — 회전 자유도 모순 (2026-07-30 코드 실측)
**문서(`IA_EDITOR_USAGE.md:93`)가 정확하다. 0/90/180/270 전부 이미 동작한다.** 패스스루가 전 구간 구현돼 있음:
- 에이전트 `Program.cs:1644`·`:2375`·`:3219` — `rotation` 숫자 파싱, 없으면 `rotated→90` 폴백
- `SheetLayout.jsx:346` — `rotation != null ? Number(rotation) : (rotated ? 90 : 0)` → `copied.rotate(-각도)`
- `npm run audit:ia-jsx` 드리프트 0 → 런타임(exe 폴더·Z:)에도 반영된 상태

낡았던 `iaEditor.js:1080` 주석("180/270 = 패스스루 필요")은 실측 결과로 정정 완료.
**spec 함의**: 회전 자유도는 계약 변경 없이 90° 스냅 4방향이 확보돼 있다. 임의 각도로 갈 때도 `placement.rotation`이 이미 숫자 필드라 출력 계약 변경은 불필요(§4-7 참조).

## 4. spec이 답해야 할 질문 (체크리스트)

1. **★입력 = 조각의 진짜 외곽선을 어디서 얻나** — **2026-07-30 실측으로 답이 좁혀졌다**
   - **ⓑ 썸네일 알파 트레이싱 = 불성립(확정).** prod R2 실썸네일 7건 실측: 투명 픽셀 **0~1.2%**, 7건 중 **3건은 알파 채널조차 없음**(PNG colorType 2). `ExtractGroups.jsx:412,460`이 `transparency=true`로 내보내도 아트워크가 **불투명 흰 배경을 포함**해 알파가 전부 불투명하다. `groups_json.edge_colors`가 전부 흰/회색인 것과 일치.
     - 흰색 제거 폴백도 실패: 잉크 성분(섬)이 5~**451개**로 파편화되고 최대 성분 면적이 bbox의 0.6~99.7%로 요동 → **재단 외곽이 아니라 디자인 내부 요소를 조각낸다.**
   - **ⓐ JSX path 추출 = 제한적.** `PackGroups.jsx:378 applyOutlineOnly`가 유일한 벡터 외곽 자산이지만 EPS 생성용이지 좌표 추출이 아니고, 원본이 임베드 래스터면(work.ai 107MB 중 벡터 0.11MB — [[design-ai-save-pdfcompatible]]) 사각 프레임만 남는다.
   - **★근본 = "잉크 외곽 ≠ 재단선".** 흰 배경 위 로고도 사각 재단이면 사각이다. 현 시스템 재단선은 전부 직사각형(`SheetLayout.jsx:412 pathItems.rectangle`·`ProcessOrderItem.jsx:470 cutlines`). **⇒ 유일하게 남은 경로 = 디자이너가 칼선을 명시하는 규약**(CutContour 스펙컬러 레이어 등)이고, 그 규약이 지금 없다. 이것이 **1차 차단 요인**이며 코드가 아니라 업무 표준 문제다.
2. **실행 위치·시간 예산** — **결정됨(2026-07-31): 별도 CEP 패널**(§7). 알고리즘 성능은 병목이 아님이 실측됨(1200²에서 10~36ms, 조각 100개 ≈ 3초).
3. **회전 자유도** — 90° 스냅 유지 vs 임의 각도(절감↑). §2 해소 결과로 **0/90/180/270은 계약 변경 없이 이미 확보**.
4. **도입 판정 기준** — 자재를 몇 % 이상 아껴야 채택인가. **prod 물량 실측(2026-07-30)이 "지금은 대상이 없다"고 말한다**:
   - 네스팅 실사용 = `sheet_layouts` **20건 전부 개발 테스트**(파일명이 `Temp\IllustratorAutomat\…`), 조각 수 **1~5개**. 조각 4~5개는 이미 prod인 수동 인터록으로 충분하다.
   - 물량 상위 = 수성 1,583라인/4,014m² · 솔벤 670 · UV 481(평균 **144×252cm** 대형) · 전사 412 · 태극기 246 — 전부 롤·사각.
   - **평판·간판은 활성 품목 0개·주문 라인 0건**(품목 마스터 미등록 단계). `finishing_methods` 7종도 전부 사각 마감이고 모양컷 항목이 없다. `post_processing` 사용 0건.
   - ⇒ **채택 트리거 = ① 칼선 규약 도입(§4-1) ② 이형 물량 발생(평판/간판/스티커 컷) ③ 자동 네스팅 실사용 정착**. 셋 다 코드 밖의 조건이다.
5. **수동 인터록과의 관계** — 대체 / 자동배치를 시작점으로 주고 수동 미세조정 유지(현 UX 철학) / 병행 토글.
6. **★하네스 판정 규칙 재정의** — 현 R4는 **bbox 분리거리** 기준이라 true-shape에선 통과해야 할 배치를 실패로 찍는다. polygon 교차 판정 + gap = Minkowski 팽창으로 다시 정의해야 하고, **이게 spec의 필수 산출물**이다(하네스 없이 패킹 손대는 것은 금지 — [[reference-nesting-harness]]).
7. **출력 계약 영향** — `placements`가 bbox+rotation인데 true-shape면 그대로 쓸 수 있나? `SheetLayout.jsx` 소비 지점까지 영향 추적 필요(에이전트 축1 = 수동 배포축이라 변경 비용 있음).
8. **다중 시트·롤 길이 단축** 규칙이 true-shape에서도 성립하는지.

## 5. 컨투어 알고리즘 — 이미 검증됨 (2026-07-30 프로토타입 실측)

무의존 프로토타입(PNG 자체 디코딩 + Moore 외곽추적 + Douglas-Peucker)으로 합성 도형 8종 측정. **원형·곡선·오목 전부 면적오차 1% 미만** — 알고리즘은 미지수가 아니다.

| 도형 | 원곽점 | 단순화(tol1) | 면적오차 | 추적 |
|---|---|---|---|---|
| 원형 r=550 | 3,108 | 79점 | **0.14%** | 36ms |
| 타원 550×300 | 2,504 | 56점 | 0.27% | 16ms |
| 별 5각 | 3,734 | 96점 | 0.42% | 13ms |
| 초승달(오목) | 3,492 | 91점 | 0.34% | 13ms |
| L자 / 삼각형 | 3,991 / 3,094 | 7 / 4점 | 0.27% / 0.25% | 17 / 11ms |

**필수 보완 2건**(spec에 반드시 반영):
- **분리된 다중 섬 = 면적오차 50.6%** — 최대 성분만 추적하면 **나머지 조각이 유실돼 잘린다**. 다중 컴포넌트 지원은 선택이 아니라 안전 요건.
- **구멍(도넛) = 25.9%** — 외곽만 추적해 구멍을 활용 못 한다. 보수적이라 안전하지만 절감 손실.

## 7. 개발 형태 결정 (2026-07-31, 용준님)

> ### ⭐ 후속 정본은 `docs/superpowers/specs/2026-07-31-cut-file-panel.md` 다
> brainstorming 결과 **요청의 진짜 목적이 "이형 네스팅"이 아니라 "재단 파일(칼선)을 직접 만드는 것"** 으로 재정의됐다.
> 지금은 어려운 라인이 외부에서 들어오고 원형·타원만 수동 제작한다 — 그 의존을 끊는 게 1차이고,
> **이형 네스팅은 칼선이 확보된 뒤의 P3**로 내려갔다. 새 패널 이름도 `com.mes.cut.panel`(재단 패널)이다.
> 이 문서(§1~§6)는 네스팅 부분의 배경 자료로 계속 유효하나, **개발 계획은 위 spec을 따를 것.**

**A0 패널에 통합하지 않는다. 별도 CEP 패널로 분리 개발 → 안정화 후 병합.**
첫 목표 = **칼선 규약 PoC + 컨투어/패킹 알고리즘 병행** → spec에서 **오프셋 엔진 P1 단일 트랙**으로 통합됨(기본 도형·타공까지 오프셋 하나로 커버되는 것이 실측돼 별도 기능이 삭제).

### 7.1 분리가 가능한 근거 (실측)
| 축 | 판정 | 근거 |
|---|---|---|
| CEP 확장 | **충돌 0** — 다른 번들 ID면 A0와 동시 설치·동시 표시 | `manifest.xml:2,5` ExtensionBundleId + Extension Id가 유일 키 |
| 호스트 로직(축2) | 새 파일 `mes-nest-host.jsx`를 Z:에 따로 두면 A0 호스트 **무변경 공존** | `host.jsx:22` 스텁이 Z: 정본을 `$.evalFile` |
| 병합 비용 | 낮음 — A0 `main.js` closure 공유 상태(`queue`·`bound`·`hostBusy`·`queueRev`)를 안 건드림 | 분할 보류 판단([[design-a0-panel-structure]])이 역으로 유리 |

### 7.2 ⚠️ 분리하면 **새로 생기는** 위험 3건
1. **크로스 패널 잠금 부재(최대 위험)** — A0의 `setHostBusy()`는 패널 내부 JS 상태라 다른 패널을 모른다. 두 패널이 일러 1개를 동시에 때리면 잠금이 통째로 무력화된다. → **ExtendScript 전역(`$.global`) 또는 잠금 파일로 승격**.
2. **params 파일 경쟁 재현** — P2에서 이미 "두 파이프라인이 `mesA0_paramsPath()` 파일 1개 공유 → 설정 섞임"이 실제 결함이었다. 새 패널이 같은 경로를 쓰면 **같은 사고가 패널 간에 재현**된다. → 경로부터 분리.
3. **감사·스모크 사각지대** — `scripts/panel-smoke.mjs:8`(PANEL 상수)·`scripts/ia-jsx-audit.cjs:70~74`(PANEL_REPO/RUNTIME/APPDATA)가 `com.mes.a0.panel` **경로 하드코딩**이다. 새 패널은 두 도구가 안 잡아 **드리프트 무방비**가 된다. → 파라미터화가 **선행 필수**(작업량 작음).

### 7.3 병합 가능성을 지키는 제약 (착수 전 확정)
- 호스트 함수 접두사 분리 `mesNest_*` — `$.evalFile`이 전역 스코프라 이름 충돌 시 A0가 깨진다
- params 경로·큐 전역(`$.global.mesA0Q` 계열)을 별도 네임스페이스로
- UI는 **A0의 탭 1개로 흡수 가능한 단위**로 설계 — 병합 시 골격만 이식되도록
