## 0. 왜 이 두 개인가 (실측 근거)

인쇄물 재단 실물 **786판**(최근 3개월, `Z:\★UV솔벤★`)을 파싱해 잡은 그림:

| 축 | 값 |
|---|---|
| 돔보 있는 판 | **98%** — 인쇄-재단 정합이 기본 |
| 판당 칼선 조각 | 중앙값 1 · **1개 57%** · 2개 이상 **43%** · 7개 이상 11% (최대 318) |
| 조각 짧은변 | 중앙값 115mm |
| 외부 제작(두용기획) | `$INSUNITS=1` 로 판별 · 338/1,912 = **18%**, 증가 추세(3월 15% → 8월 25%) — **범위 밖** |

- **도련 겹침 분할** = 조각 2개 이상인 **43%의 판**에 적용. 이형 다조각에서 재료 **12~13%** 절감(아래 §2.5).
- **단위 통일** = 전 판. 이미 의도가 코드에 있는데 **수단이 틀려 조용히 실패** 중이다(§1.1).

## 1. 단위 통일 (mm)

### 1.1 문제 — 대입이 조용히 무시된다

`SheetLayout.jsx:298` 에 이미 이렇게 쓰여 있다.

```js
newDoc.rulerUnits = RulerUnits.Millimeters; // 저장 파일 기본 단위 = mm (재단·검수 편의)
```

**의도는 맞고 수단이 틀렸다.** `Document.rulerUnits` 는 읽기 전용이라 **예외도 안 던지고 값도 안 바뀐다.**

실측 (AI 30.7):

| 수단 | 결과 |
|---|---|
| `doc.rulerUnits = RulerUnits.Millimeters` | `Points` 유지 · **예외 없음** |
| `app.preferences.setIntegerPreference("rulerType", 1)` | 환경설정은 **이미 1(mm)** 인데도 `documents.add()` 는 `Points` |
| **`app.documents.addDocument(name, DocumentPreset{units})`** | ✅ `Millimeters` 적용 |

`addDocument` 는 프로파일명이 `"[Default] Print"`·`"[기본] 인쇄"`·**존재하지 않는 이름**이어도 전부 성공했다 → 로케일 종속 위험 없음. 그래도 폴백은 둔다(조용한 실패 금지 원칙).

### 1.2 무엇이 실제로 바뀌나 — 축별 실측

| 축 | 단위를 결정하는 것 | 현재 | 조치 |
|---|---|---|---|
| **DXF `$INSUNITS`** | `ExportOptionsAutoCAD.unit` | **이미 `4`(mm)** — pt 문서·mm 문서 둘 다 `4` 로 나감(실측) | **불요** |
| **EPS** | **문서 단위를 보존** — mm 문서로 저장 → 재오픈 시 mm(실측) | 문서가 pt 라 pt | ✅ §1.3 으로 해결 |
| EPS 좌표(`%%BoundingBox`) | PostScript 규격상 **항상 point** | pt | **변경 불가·불요**(치수는 환산으로 정확히 일치) |
| 재오픈되는 `.ai`/화면 눈금 | 문서 단위 | pt | ✅ §1.3 으로 해결 |

⇒ **EPS·DXF·화면 눈금이 전부 "문서를 어떻게 만드느냐" 하나로 수렴한다.** 저장 옵션을 손댈 곳은 없다.

### 1.3 해법 — 문서 생성 헬퍼

각 호스트에 같은 내용의 헬퍼를 둔다. **사본 3벌**(배포 축이 달라 공유 불가).

이름은 **호스트 접두사 규칙을 따라 서로 다르게** 둔다 — `mesCut_newDocMM` · `mesA0_newDocMM` · `_iaNewDocMM`.
spec §5.3(재단 패널)의 "한 엔진에 두 호스트를 올려도 A0 무손상" 전제가 이 분리에 걸려 있다.
같은 이름으로 두면 나중에 한쪽만 고쳤을 때 **다른 호스트가 조용히 남의 버전을 쓰게 된다.**

```js
/**
 * mm 단위 문서를 만든다.
 * ⚠️ `doc.rulerUnits` 대입은 **예외 없이 무시된다**(AI 30.7 실측) — DocumentPreset 이 유일한 경로.
 *    이 함정 때문에 SheetLayout.jsx 가 6개월+ 조용히 pt 문서를 만들고 있었다.
 */
function mesCut_newDocMM(wPt, hPt) {   // a0 = mesA0_newDocMM · SheetLayout = _iaNewDocMM
    try {
        var dp = new DocumentPreset();
        dp.units = RulerUnits.Millimeters;
        dp.colorMode = DocumentColorSpace.CMYK;
        dp.width = wPt; dp.height = hPt;
        return app.documents.addDocument('[Default] Print', dp);
    } catch (e) {
        // 폴백 = 종전 동작(pt 문서). 단위만 잃고 기능은 그대로.
        return app.documents.add(DocumentColorSpace.CMYK, wPt, hPt);
    }
}
```

좌표는 전부 point 로 그대로 넘긴다 — **눈금 단위만 바뀌고 기하는 불변**이다(회귀 0의 근거).

## 2. 도련 겹침 분할

### 2.1 현재 규칙과 그 대가

`cut-main.js:1356`

```js
if (!buttMode && nestBleedMm > 0 && gapMm < nestBleedMm * 2) gapMm = nestBleedMm * 2;
```

간격 3 · 도련 3 을 넣으면 **간격이 6 으로 강제**된다. 사용자가 입력한 값을 덮는다.

용준님 지시(2026-08-25): **"작업자가 네스팅 시 간격을 직접 설정하는 게 좋겠다"** · **"최소 하한 두고 허용"** · 하한 **1.5mm**.

### 2.2 신규 규칙

```
BLEED_MIN_MM = 1.5                       // 업계 최소치(1/16″=1.6mm) 근처

하한 = min(BLEED_MIN_MM, 요청도련)        // ★하한이 요청을 넘지 않는다

if (맞붙임 || 요청도련 == 0)  그대로 반환
if (간격 ÷ 2 >= 요청도련)     그대로 반환          // 안 갇힌다
if (간격 ÷ 2 < 하한)          간격 = max(간격, 하한 × 2)   // 이때만 간격을 올린다
효과도련 = min(요청도련, 간격 ÷ 2)
```

- 간격 3 · 도련 3 → **간격 3 유지**, 도련 **1.5** (종전: 간격 6, 도련 3)
- 간격 6 · 도련 3 → 간격 6 유지, 도련 3 (변화 없음)
- **맞붙임(여백 0 · 간격 0)은 규칙 자체에서 제외** — 간격 0 · 도련 3 이면 **그대로 유지**한다.
  간격이 0 이라 `간격/2 = 0` 이고, 나누면 도련이 통째로 사라진다. 그리고 맞붙임에서는 도련이
  넘어가도 **옆 조각 원본이 그 위를 덮으므로**(도련은 SENDTOBACK) 안쪽 경계에는 안 보이고
  판 바깥 테두리에만 남는다 — 명함 8up 이 하는 방식이다.
- 도련 0 이면 그대로 통과 → 시트컷(무인쇄) 경로는 영향 없음.

### 2.3 왜 "분할"이 맞나

두 조각의 도련은 서로를 향해 자란다. 간격 g 의 **중앙에서 만나면 겹치지 않으면서 최대**이고, 각자 g/2 를 갖는다. 지금은 겹칠까 봐 간격을 벌리는데, 잘려 나갈 영역을 위해 재료를 더 쓰는 셈이다.

업계 정본(tilia Phoenix)도 같은 방향이다 — `spacing-type: Bleed`(도련 마스크로 간격 산정) + **`split bleed overlaps`**(겹친 도련 경로를 제품 사이에서 분할).

### 2.4 구현 지점 (구현 완료)

규칙 본체는 **순수 함수 `mesCutSplitBleed(gapMm, bleedMm, buttMode)`** 로 뽑았다.
분기가 넷(맞붙임 · 갇힘 여부 · 하한 미달 · 하한이 요청을 못 넘음)이라 소스 패턴 검사로는 동작을 못 지킨다 —
`cut:bleed` 하네스가 **브레이스 매칭으로 이 함수를 절취해 직접 돌린다**(`nesting-harness.mjs` 와 같은 수법).


| 위치 | 변경 |
|---|---|
| `cut-main.js:1356` | 강제 상향 → §2.2 규칙. `effBleedMm` 산출 |
| `cut-main.js:1550` | `growMm = offsetMm + nestBleedMm` → `offsetMm + effBleedMm` |
| `cut-main.js:1581` | `mesCut_nestApply(..., nestBleedMm, ...)` → `effBleedMm` 전달 |
| `cut-main.js:1644~` | 결과 표시에 **실제 적용 도련 mm** 명시(요청과 다르면 이유까지) |

호스트(`mesCut_nestApply`)는 인자로 받은 도련값을 그대로 쓰므로 **호스트 변경 불요** — 축2·3·4 배포 범위가 줄어든다(패널 shell 만).

래스터 도련은 조각마다 `growPx` 만큼 바깥으로 자라므로, `growMm` 을 줄이는 것만으로 **경계 분할이 그대로 성립**한다. 별도 클리핑이 필요 없다.

### 2.5 이득 (실측)

|---|---|---|
| 0px | 72~73% | 기준 |
| 3px | 65% | +11~13% |

## 3. CutContour 스팟 병행 출력 (후순위)

칼선 식별의 사실상 표준은 스팟 컬러 **`CutContour`** 다(Roland 발원 → Mimaki·Graphtec·다수 RIP). 우리는 `재단선` 레이어 + M100 0.6pt 자체 규약이라 외부 RIP 로 넘길 때 인식되지 않는다.

`doc.spots.add()` + `SpotColor` 는 AI 30.7 에서 작동 확인. 자체 규약을 **유지한 채 스팟만 추가로 입히는** 방식이라 기존 산출물과 충돌하지 않는다.

**착수 조건** = 외부 RIP 로 파일을 넘기는 실제 요구가 확인될 때. 지금은 사내 재단기가 `.ai`/`.eps`/`.dxf` 를 직접 먹으므로 급하지 않다.

## 4. 하지 말 것

- **`doc.rulerUnits` 대입** — 조용히 실패한다. 새 코드에 쓰지 말 것
- **`preferences rulerType` 으로 문서 단위 제어** — `documents.add()` 가 안 따른다(실측)
- **EPS 좌표를 mm 로 바꾸려는 시도** — PostScript 규격상 불가하고 불필요
- **`simplify menu item`** — 직전 대화상자 설정을 쓴다. 원 4앵커 → 2앵커로 뭉갠 실측 있음
- **그룹 근접 배치(거래처·색)** — 실측 손실 15%(2그룹)~113%(4그룹). 기각
- **배치 알고리즘 교체** — `step`·`tries` 노브가 이미 포화(이형 세트에서 step 4→1 차이 0). 위 항목들보다 이득이 작다
