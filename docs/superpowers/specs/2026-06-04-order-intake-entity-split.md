## 0. 한 줄 요약

**시스템은 주문을 나누지 않는다.** 한 주문 그릇에 품목별 "담당 법인"을 **사람**(법인별 게이트 코디네이터)이 지정하고, 타법인 담당 품목은 그 법인 큐로 분배. 매출은 청구 법인 하나, 타법인 공정은 내부 정산.

## 1. 방향 전환 기록 (왜 강제분리를 폐기했나)

- **초기 설계**: 수주(상위) → 법인별 주문서(하위) 2단, 카드그룹으로 **법인 자동 판정**, 6 Phase.
- **폐기 이유 — 생산이 물리적으로 섞인다**:
  - 간판(선명) 완제품 **안에** 출력물(동산 후렉스/시트)이 **부품으로** 들어감 = 한 제품에 두 법인 공정. 품목 단위로 칼같이 못 나눔.
  - 현수막/솔벤은 간판에 안 들어가는 **독립 품목**이지만, 원단·단가는 동산 전문 → 또 별도 상황.
  - 케이스가 무한 분기(결합/독립/전문성) → **규칙 기반 자동분류 불가**.
- **핵심 통찰**: 자동 분류를 포기하면 늪에서 나온다. **시스템 = 나누는 주체가 아니라 섞임을 담는 그릇. 판단은 사람이.**
- 용준님 말("강제 분리하려니 시스템 충돌이 심각")이 정확. 강제 분리 자체가 충돌의 원인이었음.

## 2. 근본 문제 재정의

- 두 법인을 나눈 **목적 = 회계·세무 독립**(멀티엔티티 설계 `2026-04-22`). 생산은 섞여도 되고, **회계만 정확히 귀속**되면 됨.
- 결합 제품: **최종 법인이 완제품 판매**(고객 매출 = 최종 법인), 타법인 공정 = 법인 간 내부 거래. 회사는 이미 *"물건 교류 빈번 → 월말 상계 → 차액 세금계산서"*로 운영(멀티엔티티 문서).
- → 시스템이 주문을 강제로 쪼개는 것 자체가 틀린 방향. 안 쪼개고, **누가 무슨 공정을 했는지 기록 + 정산 보조**가 정답.

## 4. 코디네이터 모델

- **창구 = 법인별 게이트(현행 수신 유지)**: 거래처가 보낸 법인의 코디네이터가 받음. 거래처 습관 안 바꿈. (단일 창구로도 확장 가능하나 출발은 법인별)
- **코디네이터 = 역할**(신규 채용 아님). 주문 많이 다루는 사람/실장급 겸직. 백업 지정 권장.
- **책임 범위 = 수신 → 품목 파악 → 담당 지정 → 분배까지.** 규격·단가·작업지시는 **담당 디자이너**(아는 사람이). → 코디네이터가 전 품목 전문지식 불필요.
- **권한**: 코디네이터는 분배 위해 **타법인 주문까지 열람**(교차 가시성). 일반 디자이너는 자기 담당만.

## 5. 데이터 모델 (기존 확장, 신규 테이블 최소)

```sql
-- 품목별 담당 법인 (생산/공정 담당). 사람이 지정, 자동은 추천.
ALTER TABLE order_items ADD COLUMN assigned_entity_id INTEGER;     -- 담당 법인
ALTER TABLE order_items ADD COLUMN assignment_status TEXT;          -- NULL | PENDING | ACCEPTED | REJECTED
-- orders.entity_id = '청구 법인'(완제품 판매/접수 법인) 의미로 유지 → 매출 귀속
-- cards.requesting_entity_id (기존, 0150) = 타법인 공정 카드 표현에 재사용
```

- **`orders.entity_id` = 청구(매출) 법인** / **`order_items.assigned_entity_id` = 생산·공정 담당 법인** → 매출과 생산 담당을 **분리**. 이게 결합 제품(매출=최종, 공정=섞임)을 자연 표현.
- 내부 정산 집계 테이블은 Phase 4에서(타법인 담당 공정값 합산 → 월말 상계 보조).
- **receipts/receipt_files/card_group_entity_map 신규 테이블 = 불필요**(폐기). 카드그룹→법인은 "강제 매핑"이 아니라 "담당 자동 추천"으로만 사용(사람이 수정 가능).

## 7. 매출 · 내부정산

- **청구(매출)** = `orders.entity_id` 하나(완제품 판매/접수 법인). 세금계산서도 이 법인.
- **타법인 담당 공정** = 내부 거래. 월말 동산↔선명 기여 집계 → 상계(회사 기존 관행과 정렬).
- **독립 제품 청구 분리**(한 주문에서 고객 매출을 두 법인으로 진짜 나눔)는 **후속/드묾** → 필요 빈도 높으면 그때 "그 품목만 별도 주문 분리" 보조. (현재는 청구 법인 단일 가정)

## 10. 미결 / 후속

- ~~**재고차감 entity 기준**(점검 #3)~~ **✅ 결정·구현·배포(2026-06-04)**: **담당 법인 우선** — 재고는 물리적 실체이므로 자재를 실제 보유·소비한 법인(담당) 재고에서 차감해야 매출(청구법인)/재고(담당법인)/내부정산이 3분리 정합. `COALESCE(assigned_entity_id, orders.entity_id)` 전환(출고 `stockShip.ts` 라인별, 생산 `autoDeductInventory.ts`는 `cards.requesting_entity_id` 기준). 담당법인 재고 row 부재 시 `INSERT OR IGNORE`로 0 생성 후 음수 차감. `inventory_auto_deductions.entity_id` 보정. 일반 주문(assigned NULL)은 청구법인 fallback=회귀 0.
  - **실증(로컬 E2E, 배포 함수 SQL)**: 현실적 혼합주문(다른 품목→다른 담당) 정상 — 담당 선명품목 entity2 −5, 청구품목 entity99 −3, 거래기록 entity별 분리.
  - **⚠️ 엣지 발견·수정(마이그 0293)**: `inventory_transactions` 부분 UNIQUE 인덱스가 `entity_id` 미포함 → **같은 품목**을 한 주문에서 복수 법인 담당으로 분할 시 stockShip item단위 dedup이 두 번째 그룹 silent skip(한 법인만 차감). **수정**: 인덱스에 `entity_id` 추가(`0293`, DROP+CREATE만) + dedup `AND entity_id=?`(주문×품목×법인 멱등). 재검증 PASS(같은 품목 99→97·2→95, 거래기록 2행).
- **독립 제품 청구 분리**: 한 주문에서 고객 매출을 두 법인으로 나눠야 하는 빈도. 높으면 보조 설계 추가.
- **내부 정산 단가 기준**: 타법인 공정값을 어떻게 산정(단가표? 협의가?).
- **담당 자동추천 정확도**: 카드그룹 기반 추천의 적중률 — 운영하며 보정.
- **거래처 셀프 포털**(P5): 별도 대형 프로젝트. 지금 그릇 구조가 기반이 됨.
- **결합 vs 독립 비중**: 용준님 미파악 → 운영하며 실제 데이터로 확인. 독립 비중이 매우 높으면 §11 일부 재검토.

## 11. 폐기된 설계 (참고용 — 되살리지 말 것)

초기 "강제 분리" 설계의 다음 요소는 **폐기**:
- 수주(receipts) 상위 테이블 / receipt_files / card_group_entity_map(강제 매핑)
- 주문 법인별 분할(2단 구조)
