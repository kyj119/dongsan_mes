## 1. 왜 (진짜 목적)

**재단 파일(칼선)을 직접 만들 수 있게 되는 것**이 1차 목적이다.

현재 상태 = 원형·타원 같은 단순 형태만 수동 제작하고, **어려운 라인은 만들어진 파일이 외부에서 들어온다**. 이 의존을 끊는 것이 이번 작업이고, 이형 네스팅은 칼선이 확보된 **뒤에** 얹히는 후속이다(P3).

> 우선순위 재정의: ① 칼선 직접 제작 → ② 이형 네스팅 → ③ 시안 작업 대행(향후, 이 spec 범위 밖이나 설계가 막지 않을 것)

## 2. 현황 실측 (2026-07-30~31)

### 2.1 재단 작업은 2종류

| 종류 | 장비 | 산출물 | 실측 경로 |
|---|---|---|---|
| 시트 컷팅 | 플로터 | `.ai`/`.eps` — **인쇄물 없이 컷 라인만** (100~400KB 순수 벡터, 임베드 래스터 0) | `Z:\★시트 CUT★\완료\` |
| CNC 재단 | CNC | `.eps`(인쇄) + **`.dxf`(재단) 쌍** | `Z:\★UV솔벤★\…\16-(포맥스3T+자동바니쉬)…\` |

시트컷 파일명 실측 = "동반고해소·검사안내·운영시간·시간표·번호·씨씨티비" → **주류는 글자/로고 컷팅**이다. 즉 병목의 큰 덩어리가 래스터가 아니라 **벡터 실루엣**이고, 이는 Image Trace 없이 처리된다.

### 2.2 재단 파일에 표준 규약이 없다

| 대상 | 실측 |
|---|---|
| 시트컷 `.ai` | 스펙컬러 **0개**, 레이어 = `"레이어 1"`(기본값), CutContour 키워드 **0** |
| CNC `.dxf` | `$INSUNITS=4`(**mm**), AC1015. 레이어명은 기본값이나 **역할은 분리됨** — 외곽 SPLINE=`Layer 2`, 돔보 CIRCLE=`Layer 3` |
| DXF 엔티티 | SPLINE(degree 3·제어점 142) + CIRCLE + HATCH(채워진 원의 부산물) |

**⇒ 새 규약과 충돌할 기존 규약이 없다.** 사내 출력 규약(레이어 `'재단선'` · M100 실선 0.6pt)을 그대로 쓴다 — `mes-a0-host.jsx:31`·`:537~549`, `mes-sheet.jsx:382~394`.

### 2.3 DXF의 6mm 원 = 돔보 (우리가 만든 것)

코드와 소수점까지 일치 확인:

| 항목 | 코드 | DXF 실측 |
|---|---|---|
| 지름 | `mes-a0-host.jsx:553` `DOMBO_DIAM = 6mm` | 전량 6.00mm |
| 중간 간격 X | `:566` `n=floor(1214.0/500)=2` → `step=1214.0/3=404.67` | 404.7 |
| 중간 간격 Y | `n=floor(2064.0/500)=4` → `step=2064.0/5=412.8` | 412.8 |
| 방향마크 | `:578` `DIR_OFFSET=60mm` | 108.7+60 = 168.7 |

**⇒ 돔보는 A0 패널이 이미 수행한다. 재단 패널에서 재구현하지 않는다**(§8 금지사항).

### 2.5 ★실물 생산 DXF 의 레이어 구조 (2026-08-02 실측)

`Z:\★UV솔벤★\2026년\08월\03일\01-나무그리고\(포맥스5T+자동바니쉬)…242x120….dxf` (07-31 생산):

```
TABLES   : 0 / "Layer 2" / "Layer 3"
BLOCKS   : SPLINE ×37  (Layer 2)          ← 칼선 본체
           CIRCLE ×4 + HATCH ×4 (Layer 3)
ENTITIES : INSERT ×1   (Layer 2)          ← 칼선 블록 참조
           INSERT ×2 + CIRCLE ×13 + HATCH ×13 (Layer 3)  ← 돔보
```

읽어낼 것 3가지:

1. **역할이 레이어로 분리돼 있다** — 칼선 `Layer 2` · 돔보 `Layer 3`. 이름은 일러 기본값이므로 **이름 규약이 아니라 분리 자체가 규약**이다(§2.2와 일치). 우리가 `재단선`·`돔보`처럼 의미 있는 이름을 붙여도 된다.
2. **블록 구조가 정상이다** — 칼선 SPLINE 은 BLOCKS 안에 있고 ENTITIES 는 INSERT 로 참조한다. 재단기가 이걸 읽고 잘라 왔다.
3. **돔보는 CIRCLE + HATCH 쌍** — 채워진 원의 부산물로 HATCH 가 같이 나온다(개수 일치: 13+13, 4+4).

**전수 조사 12건 (2026-08-02 · `Z:\★UV솔벤★\2026년\07~08월`)**

| 항목 | 실물 | 우리(수정 전) |
|---|---|---|
| 레이어 | **12/12 역할 분리** — `0·Layer 2·Layer 3` ×9 · `0·출력파일 앉힐곳·재단파일·재단마크` ×1 · `0·레이어 1·cut·레이어 3` ×2 | `0·재단선` **1개** ❌ |
| DXF 버전 | **12/12 AC1015**(AutoCAD 2000) | AC1021 ❌ |
| 단위 | CNC 9건 `INSUNITS=4`(mm) · 솔벤시트 3건 **`1`(inch)** — 자기들끼리도 갈린다 | 4(mm) ✅ |
| 돔보 | CIRCLE + HATCH **쌍**(채워진 원의 부산물) | 동일 ✅ |
| 블록 | 대부분 평평(ENTITIES 직속) · 34/12/4/2 개가 블록인 파일도 있다 | 그룹 해제 후 평평 ✅ |
| 레이어명 인코딩 | ASCII 9건 · 한글 3건은 `_U+XXXX` 이스케이프 | 원시 cp949(`$DWGCODEPAGE=ANSI_949`) ⚠️ |

**⇒ 맞춘 것 3가지** (`mesCut_exportDxf`)

1. **AC1015 로 낮춤**(`AutoCADRelease15`) — 13/14/15 셋 다 AC1015 이고 내용·크기가 같다(6개 옵션 전부 내보내 확인). 낮춰서 잃는 게 없고, **우리만 다른 버전**으로 나가는 위험이 사라진다.
2. **DXF 안에서만 레이어 2개로 분리** — 칼선 `CUT` / 마크 `MARK`. 판정은 크기(지름 6mm±2·정사각, `mesCut_isMarkItem`). **일러 문서는 계속 `재단선` 하나** — 작업자에게 레이어를 늘리지 않는다.
3. **레이어명을 ASCII 로** — 이름엔 규약이 없으니(9/12 가 `Layer 2/3`) 인코딩 변수를 아예 없앤다.

검증: `0|CUT|MARK` · AC1015 · unit 4 · CUT=SPLINE+LWPOLYLINE · MARK=CIRCLE5+HATCH5 · 블록 0.

**★개체 자체 설정 (엔티티 단위 전수 · 2026-08-02)** — 레이어 속성이 아니라 **여기에 규약이 있다**.

| | 실물 12건 | 우리 |
|---|---|---|
| 돔보 원 | ⌀**6.00mm** 전량 · 색 **BYLAYER** · 선폭 BYLAYER · **HATCH 동반**(채워진 원) | ⌀6mm · BYLAYER · HATCH ✅ |
| 칼선 | 색 **230 개별 지정**(BYLAYER 아님) · 선폭 0/18/158 제각각 | 색 **230** ✅ · 선폭 20 |
| 레이어 속성 | 12/12 `color 7 · Continuous · lw 0|-3` — **구분 정보가 전혀 없다** | 동일 |
| 타공 | 경고판 2건: CIRCLE ⌀**10mm** 이 **칼선 레이어**에 색 230 | 획 원 → CUT ✅ |

**⇒ `mesCut_isMarkItem` 을 크기 판정에서 채움 판정으로 바꿨다.** 실물이 **타공도 원**으로 두기 때문이다 — 크기로 가르면 6mm 이하 타공이 마크 레이어로 새어 나가 **재단기가 안 자른다**. 우리 산출물에서 둘은 스타일이 정반대라(돔보=채움·획 없음 / 타공·칼선=획·채움 없음) 채움이 정확한 기준이다. 크기는 보조 가드로만 남겼다.

실기 확인(타공 ⌀6mm 획 원 + 돔보 5개 동시): 타공 → `CUT`(색 230) · 돔보 → `MARK`(BYLAYER + HATCH) ✅

**아직 안 맞춘 것**: 시트컷 계열(`Z:\★시트 CUT★`)은 `.ai` 752 · `.eps` 60 이고 **DXF 가 0개**다 — 플로터는 `.ai`/`.eps` 를 직접 먹는다(§2.1). 그쪽 규약은 별도 확인이 필요하다.

### 2.6 ★시트컷(플로터) 파일 — **규약이 사실상 없다** (2026-08-02 실측 6건)

`Z:\★시트 CUT★` = `.ai` **752** · `.eps` **60** · **DXF 0개**(플로터는 `.ai`/`.eps` 를 직접 먹는다). `.ai` 는 전부 PDF 1.5 압축 스트림이라 평문 파싱이 안 된다 → **일러로 열어** 읽었다(읽기 전용·저장 없이 닫음).

| 파일 | path | 획만 / 면만 | 획색 | 획폭(pt) | 6mm원 | 아트보드 vs 아트 |
|---|---|---|---|---|---|---|
| 명성-미투미용실 컷팅+도안 | 85 | 1 / 83 | K100 | 0.57 | 4 | 637×466 vs 341×358 |
| 프랜즈 | 166 | 2 / 164 | C64M69Y68K79 | 0.26 | 0 | 210×297 vs **920×120** |
| 푸른광고-제이다락방 컷팅 | 250 | **213** / 37 | K100 | **0.05** | 14 | 210×297 vs 119×93 |
| 스타벅스 대전유성구청점 | 101 | 31 / 70 | K100 | **0.06** | 0 | 420×297 vs 100×144 |
| 디자인바 | 10 | 0 / 10 | — | — | 0 | 752×562 vs 83×32 |
| 탑_선병원 | 118 | 5 / 112 | **C100**·K100 | 1 / 0.57 / 0.7 | 3 | 559×386 vs 503×434 |

**읽어낼 것 5가지**

1. **칼선을 표시하는 규약이 없다** — 색(K100·시안·CMYK 검정)도 선폭(0.05~1pt)도 제각각이고 **CutContour 스팟은 0**이다. 스팟 1개짜리는 전부 `[Registration]`(맞춰찍기) — **일러가 모든 문서에 기본으로 넣는 스와치라 아무 의미가 없다**.
2. **주류는 "선"이 아니라 "면"** — 6건 중 5건이 면 위주다. §6.27 의 선 도안 판정은 **반대 방향 케이스**(면 0)를 다루므로 둘 다 필요하다.
3. **칼선만 담은 파일은 극세선으로 온다** — 0.05~0.06pt 획 213개/31개(푸른광고·스타벅스). 이게 §2.1 이 말한 "컷 라인만" 파일이다.
4. **돔보 규약 없음** — 6mm 원이 0~14개로 들쭉날쭉하고, 14개짜리는 9mm 이하 정사각이 163개라 글자 요소 오탐일 가능성이 크다.
5. **아트보드를 안 맞춘다** — A4 기본에 920mm 아트가 들어 있는 파일까지 있다.

**⇒ 판단**: 지켜야 할 강제 규약이 없으므로 **우리 규약(`재단선` 레이어 · M100 0.6pt)을 그대로 유지한다.** 대신 §2.1 이 요구하는 것은 **"칼선만 있는 파일"** 인데 지금 그렇게 나가는 건 DXF 뿐이다 → 시트컷용 **칼선만 `.ai`/EPS 내보내기**가 빠져 있다(`mesCut_exportDxf` 의 임시문서 방식을 그대로 재사용하면 된다).

### 2.7 ★CNC(포맥스 등) 작업 폴더 형식 — **EPS + DXF 같은 이름 쌍** (2026-08-02 실측)

예: `Z:\★UV솔벤★\2026년\06월\25일\방문,직배\11-(포맥스5T+자동바니쉬)디자인인코-총50장-30일 오후직배\`

```
(포맥스5T+자동바니쉬)쓰레기불법투기(103x206-6장).eps   8,429KB   ← 판(인쇄)
(포맥스5T+자동바니쉬)쓰레기불법투기(103x206-6장).dxf     196KB   ← 같은 판의 칼선
(포맥스5T+자동바니쉬)쓰레기불법투기(62x83-1장).eps     7,258KB
(포맥스5T+자동바니쉬)쓰레기불법투기(62x83-1장).dxf       179KB
```

| 규칙 | 실측 |
|---|---|
| 폴더명 | `<순번>-(자재+후가공)<거래처>-<수량>-<납기/배송>` |
| 파일명 | `(자재+후가공)<품목>(<W>x<H>-<장수>장)` — **W×H 는 판 전체 크기이고 단위는 cm** |
| 쌍 | **EPS 와 DXF 가 확장자만 다른 같은 basename** |
| DXF 유무 | 재단이 있는 판에만 붙는다 — 폴더 구성이 `.eps만` 이거나 `.eps + .dxf`(EPS 수 ≥ DXF 수) |
| `.ai` | **작업 폴더에 두지 않는다**(6월 표본 22폴더에서 0건) — 원본은 다른 곳, 여기엔 최종 산출만 |

**검증**: 파일명 `103x206` ↔ EPS `%%HiResBoundingBox 2919.69×5839.37pt` = **1030.0×2060.0mm** 정확히 일치(`62x83` → 620×830mm 도 동일).

**★이 파일들은 이미 우리 파이프라인 산출물이다** — 돔보 개수가 `mesCut_addDombo` 규칙과 정확히 맞는다:
`620×830` → 코너4 + 방향1 + 중간(620·830 각 1개씩×2변) = **9개** = 실측 9 · `1030×2060` → 4+1+(2×2)+(4×2) = **17개** = 실측 17.

**⇒ 재단 패널이 맞춰야 할 산출 규약**
1. 네스팅 시트는 **EPS + DXF 를 같은 basename 으로 같은 폴더에** 내야 한다(지금은 둘 다 없다 — 새 문서로만 남는다).
2. 파일명에 **판 크기(cm) + 장수**가 들어간다.
3. 단품 칼선의 DXF 도 `%TEMP%\<ASCII 깨진 이름>_cut.dxf` 가 아니라 이 규칙을 따라야 한다(§9-7 의 답).

### 2.8 작업 폴더 산출 구현 (2026-08-02)

`[작업 폴더로 내보내기 (EPS+DXF)]` — 네스팅 시트를 §2.7 규약대로 한 쌍으로 저장한다.

| 요소 | 처리 |
|---|---|
| 파일명 | `(자재+후가공)품목(<W>x<H>-<N>장)` · 자재·후가공은 **6~7월 작업 폴더명에서 뽑은 실제 값**을 datalist 로 제시 |
| 규격 | **호스트가 돌려준 실제 아트보드 크기**(`nestApply` → `sheetw/sheeth`) |
| 폴더 | 호스트에서 `Folder.selectDlg` — 마지막 폴더를 기억한다 |
| 이름 전달 | **params 파일(UTF-8)** — 한글이라 evalScript 인자로는 깨진다 |
| EPS 옵션 | A0 와 동일(`cmykPostScript`·`ILLUSTRATOR10`·`COLORTIFF`·`embedAllFonts`) |

**함정 2건**

1. **파일명 규격에 시트 프리셋을 쓰면 안 된다** — `nestApply` 가 아트보드를 배치 bbox + 돔보 여백으로 줄이므로 프리셋 1370 을 쓰면 이름(137)과 파일(136.5)이 어긋난다. 실물은 파일명 규격 = EPS 바운딩박스로 **정확히 일치**한다.
2. **★비활성 문서의 `artboards[0].artboardRect` 는 활성 문서 값을 돌려준다** — 시트가 312×273 인데 원본 문서 크기 600×400 이 나왔다. 시트가 활성일 때(루프 안에서) 읽어야 한다.

실기 검증: 한글 파일명 그대로 저장 · EPS 첫 4바이트 `C5D0D3C6`(실물과 같은 DOS 바이너리 EPS + TIFF 미리보기) · DXF 185KB(실물 179~206KB) · `sheetw/sheeth` 가 아트보드와 일치(312/274 ↔ 312.21×273.62).

**미해결**: 판이 여러 개면 **첫 판만** 나간다(실물도 판마다 파일이 따로다) — 파일명 옆에 그 사실을 표시한다.

### 2.9 ★재단선 ↔ 여백 ↔ 디자인 크기 — 실측 30쌍 (2026-08-02)

EPS·DXF 쌍이 같은 폴더에 같은 이름으로 있으므로 **인쇄물과 칼선을 직접 대조**할 수 있다. 6~8월에서 474쌍 중 30쌍(솔벤시트 16 · 포맥스/폼보드 14)을 쟀다.

```
   ┌─────────────────────────────┐  ← 인쇄물(EPS) = 파일명 규격
   │  ┌───────────────────────┐  │
   │  │                       │  │  ● 돔보 중심 = 재단선 + 7mm
   │  │      재단선(DXF)       │  │    (⌀6 이므로 바깥끝이 인쇄물 가장자리에 접한다)
   │  │                       │  │
   │  └───────────────────────┘  │
   └─────────────────────────────┘  인쇄물 − 재단선 = **변당 10mm**
```

| 관계 | 실측 | 표본 |
|---|---|---|
| 인쇄물(EPS) − 재단선(DXF) | **변당 10.00mm** | 30쌍 중 26쌍 정확히 10.00 (나머지는 소형 판 반올림) |
| 돔보 중심 − 재단선 | **7mm 바깥** | 전량 일치 |
| 돔보 원 바깥끝 | 7+3 = **10mm** = 인쇄물 가장자리와 **정확히 접함** | — |
| 파일명 규격 | **인쇄물 크기**(cm) — 재단선이 아니다 | 예 `82x132` ↔ EPS 820×1320 · 칼선 800×1300 |

**★우리 상수와 모순되지 않는다 — 기준점이 다를 뿐이다.** 사내 생성기 4개(`SheetLayout`·`mes-sheet`·`mes-a0-host`·`mes-cut-host`)는 전부 `CORNER_DIST = 17mm`인데, 그건 **디자인 바운드 기준**이다. 실물을 디자인 기준으로 환산하면:

```
디자인 → 재단선 10mm → 돔보중심 +7 (= 디자인+17 ✅ 우리 상수) → 원 바깥끝 +3 (= 디자인+20 = 인쇄물 끝)
```

**⇒ 도련 수치의 답 = 10mm.** 색을 고르는 문제가 아니었다 — 실물은 **재단선 바깥으로 10mm 더 인쇄**해 재단 오차를 흡수한다. 사내 기존 도련 자산 2개도 색을 고르지 않는다:

| 자산 | 방식 |
|---|---|
| `SheetLayout` 도련 v5 | Design 그룹의 **클립 사각을 밖으로 밀어** 원본 그림이 더 드러나게 (사각 4점 클립만 · 실패 시 스케일 폴백) |
| `ProcessOrderItem` edge_strip | 가장자리 **1mm 띠를 복제해 늘려** 바깥에 붙임 (방향별 · 원본 무변경) |

둘 다 **사각 전용**이라 이형 실루엣에는 그대로 못 쓴다 → 이형용은 "확대 사본을 오프셋 실루엣으로 클리핑해 원본 뒤에 깔기"가 같은 원리의 변형이다(미구현).

⚠️ **우리 판 여백은 실물보다 넓다** — 네스팅 산출 실측: 아트보드 − 시트 테두리 = **23mm/변**(실물 10mm). 롤 1370 기준 변당 13mm × 2 = **26mm 손실**. 다만 우리 아트보드는 돔보 여백(17+6)을 그대로 두른 것이라 규칙상 자연스러운 값이고, 실물은 돔보를 인쇄물 가장자리에 붙여 10mm 로 끝낸다. **어느 쪽을 표준으로 삼을지는 운영 판단**이다.

### 2.11 ★도련 — 실측 3mm, 구현 (2026-08-02)

**정정**: 앞서 "인쇄 − 칼선 = 10mm = 도련"으로 적었으나 **틀렸다**. 그 10mm 는 **돔보 자리**다(중심 7mm + 반지름 3mm). EPS 바운딩박스가 돔보 바깥끝과 정확히 일치한다.

**진짜 도련은 클립 패스를 읽어야 나온다** — clipped 그룹의 `visibleBounds` 는 클립 크기가 아니라 원본 크기를 돌려주므로 클립 패스의 `geometricBounds` 를 직접 읽는다.

| 파일 | 칼선 | 인쇄(클립) | 도련 |
|---|---|---|---|
| 음악사랑 82x132 | 800×1300 | **806×1306** | **3.00mm** |
| 노랑통닭 신두리 108x70 | 1060×680 | **1066×686** | **3.00mm** |
| 호국보훈 헌혈증서 73x62 | 710×600 | 716.7×618.6 | ~3.4mm |

**★실물은 도련을 합성하지 않는다 — 원래 있던 그림을 더 드러낸다.** 음악사랑 파일의 클립(806×1306) 안에는 **3134×2056 짜리 원본 래스터**가 들어 있었다. 사내 자산 둘 다 같은 원리다(색을 고르지 않는다):

| 자산 | 방식 |
|---|---|
| `SheetLayout` 도련 v5 | Design 그룹의 **사각 클립을 밖으로 밀어** 원본이 더 드러나게 |
| `ProcessOrderItem` edge_strip | 가장자리 **1mm 띠를 복제해 늘려** 바깥에 붙임 |

**구현 = 2경로** (`mesCut_vecBleed`)

1. **클립 확장(우선)** — 아트에 **사각 4점 클립**이 있으면 `여백 + 도련`만큼 밖으로 민다. 왜곡·빈 곳 0. 실물과 같은 수단.
   - ⚠️ 넓히는 양이 `도련`만이면 인쇄 끝이 칼선과 겹쳐 **도련이 0**이 된다(실측에서 걸림). `여백 + 도련`이어야 한다.
   - ⚠️ **사각 클립만** 다룬다 — 임의 형상 클립에 효과를 걸면 `clipping` 플래그가 깨질 수 있다.
2. **확대 폴백** — 클립이 없으면 아트 사본을 도련 경계까지 비균일 확대 → 경계로 클리핑 → 원본 뒤로.
   - ⚠️ **이형에서 링이 빈다.** 합집합 산술로 실측: 별(뾰족) **19.8%** · L자(오목) 7.7% · 가는목 0%.
   - 그래서 결과창에 **어느 방식을 썼는지 반드시 표시**한다(clip=무손실 / scale=근사·경고).

**검증**: 클립 케이스 100×80 → 칼선 106×86 · 인쇄 112×92 = **도련 3mm/변** ✅ · 클립 없으면 `bleed=scale` 폴백 ✅ · `cut:smoke` 166/166.

## 4. 핵심 기술 — 오프셋 엔진 (실측 검증 완료)

### 4.1 파이프라인

```
① 대상 선택(일러)  →  ② 마스크 생성  →  ③ 거리변환(EDT)  →  ④ 임계 = 오프셋
                        ├ bbox 모드                              ↓
                        ├ 실루엣 모드(벡터)                  ⑤ 컨투어 추적
                        └ 래스터 트레이스(P2)                     ↓
                                                            ⑥ 단순화(Douglas-Peucker)
                                                                 ↓
                                                   ⑦ '재단선' 레이어 M100 + DXF
```

②만 모드별로 다르고 ③~⑦은 공통이다. **이것이 P1·P2를 하나로 묶는 근거**다.

### 4.2 커버리지 실측 (오프셋 30px 기준)

| 도형 | 팽창량(기대 30) | 코너반지름 | 섬 | 외곽점 | ms |
|---|---|---|---|---|---|
| 정사각 400 | **30.0** | 12.7 | 1 | 17 | 44 |
| 원 r=200 | **30.0** | — | 1 | 35 | 37 |
| 타원 250×120 | **30.0** | — | 1 | 32 | 41 |
| 삼각형 | **30.0** | — | 1 | 16 | 37 |
| L자(오목) | **30.0** | 12.7 | 1 | 22 | 33 |
| 분리 2섬(간격 60) | **30.0** | 12.7 | **1(병합)** | 31 | 35 |

- **사각형 + 오프셋 = 라운드사각 자동 생성** — 실측 코너반지름 12.7 ↔ 이론 `R(√2−1)=12.4`
- **섬 병합 임계 = 정확히 gap/2** — 간격 60px에서 29px 2개 / **30px 1개**
  → 실무 규칙: **글자가 낱개로 흩어지지 않게 하려면 오프셋 ≥ 자간/2**
- 컨투어 정확도는 별도 실측에서 원형 오차 **0.14%**, 별·초승달·L자 전부 1% 미만

### 4.3 해상도 = 비용 (설계 제약)

| 대상 | 해상도 | 픽셀 | EDT | 메모리(Float64) |
|---|---|---|---|---|
| 시트컷 79×14cm | 0.25mm/px | 1.8M | 91ms | 27MB |
| CNC 판 122×207cm | 1.0mm/px | 2.5M | 124ms | 39MB |
| CNC 판 122×207cm | **0.5mm/px** | 10.1M | **524ms** | **154MB** |
| CNC 판 122×207cm | 0.25mm/px | 40.4M | 2,501ms | 617MB |

CEP는 CEF(Chromium) 안이라 메모리 제약이 있다. **0.5mm/px 상한**, Float32로 메모리 절반, 판 크기별 자동 선택. 재단 정밀도 ±0.5mm는 칼날 폭·재료 신축보다 작아 실무상 충분하다.

### 4.4 타공도 같은 엔진

내부 오프셋(인셋) → 그 경로 위 등간격 배치로 산출된다. 실측: 정사각 인셋 30px → **코너 4 + 변 중앙 4 = 8점** 정확 배치, L자(오목)도 정상. 별도 알고리즘 불요.

### 4.5 구멍(내부 홀) — 글자 컷팅의 필수 요건

**구멍 = 배경(0) 연결요소 중 이미지 테두리에 닿지 않는 것.** `components()` 재사용으로 얻는다.

이게 없으면 `ㅇ·ㅁ·ㅂ·ㅎ·0·8·A·B` 속이 안 뚫린다 — **시트컷팅 주류가 글자라 실무에서 바로 문제가 된다.**

| 도형 | 구멍 추출 전 면적오차 | 후 |
|---|---|---|
| 도넛 | 29.5% | **0.16%** |
| 액자(사각+사각구멍) | 22.9% | 0.20% |
| **`ㅇ`자** | **53.2%** | **0.18%** |
| 구멍 2개 | 12.6% | 0.12% |
| 원(구멍 없음) | — | 구멍 **0개**(오탐 없음) |

**★오프셋 적용 뒤 마스크에서 뽑아야 한다** — 그래야 구멍이 함께 축소되고, 오프셋이 구멍 반지름을 넘으면 사라진다(칼날이 못 들어가는 물리와 일치). 실측(구멍 반지름 180px):

```
offset=20  → 반지름 160 (기대 160)      offset=150 → 30 (기대 30)
offset=60  → 120        (기대 120)      offset=200 → 구멍 소멸 ✅
```

**최소 구멍 크기 필터가 필수다**(`MIN_HOLE_MM`, 잠정 2mm) — 글자 사이 좁은 틈이 오프셋으로 막히면 갇힌 배경이 미세 구멍으로 잡힌다. 실측: 한글 6줄에서 **구멍 144개** → 2mm 필터 후 120개(최소 3mm·중앙값 17.2mm·5mm 미만 12개). 칼날이 들어갈 수 없는 크기는 재단선이 아니라 노이즈다.

일러에는 **compound path**로 그린다(`compoundPathItems`) — 재단 자체는 개별 닫힌 경로여도 되지만, 작업자가 화면에서 구멍을 확인할 수 있어야 한다. 실패 시 개별 경로 폴백.
`assignHoles()` 가 구멍을 **가장 작은 포함 bbox** 의 외곽에 배정한다(외곽이 중첩돼도 안쪽에 붙는다).

### 4.6 알려진 갭 1건

거리변환 오프셋은 **항상 라운드 조인**이라 뾰족한(miter) 코너가 나오지 않는다. 재단에서는 라운드가 오히려 정상(뾰족한 끝은 찢어짐)이나, 직각 사각 칼선이 반드시 필요하면 별도 경로가 필요하다 → §9 미해결.

```
[호스트] mesCut_exportDxf(path)       mm·AC 최대 편집성
```

- **배경을 흰색이 아니라 투명으로 굽는다** — 흰 배경으로 구우면 '흰색 잉크'와 배경을 구분할 수 없다(실측에서 확인된 함정).
- **임시 문서에 복제해서 굽는다** — 현재 문서 아트보드를 건드리면 사용자 작업이 오염된다.
- **기존 `'재단선'` 레이어 내용을 지우지 않는다** — 사용자가 손으로 넣은 선이 있을 수 있다.
- 단순화 tol = 0.4mm 상당(플로터·CNC 가 읽기 좋은 점 수), 해상도는 `pickResolution` + 0.5mm/px 상한.
- DXF 경로는 **호스트가 정한다**(`mesCut_dxfPath()`) — 작업 폴더 규칙이 확정되면 한 곳만 고치면 된다.

**검증**: `cut:smoke` **37/37**(P0 27 + P1 10). 파이프라인 순수 계산부를 `window.__mesCutBuild` 로 노출해 **일러 없이** 회귀를 잡는다 — 오프셋 적용·mm 좌표 범위·타공 8개·지름 6mm·**떨어진 조각 2개 모두 보존**. `cut:bench` 통과. `audit:ia-jsx` 4축 0(geometry.js 편입).

### 6.7 ★실동작에서만 드러난 함정 4건 (전부 수정 완료)

코드 리뷰나 헤드리스 스모크로는 **하나도 못 잡았을** 것들이다. 실파일로 돌려봐야 나왔다.

1. **문서 간 `duplicate` 는 원본 문서가 active 일 때만 동작한다** — `documents.add()` 가 새 문서를 active 로 만들어 버려 복제가 0건이 됐다. **예외를 던지지 않아** try/catch 로 못 잡는다. 같은 아이템·같은 호출로 실측: `duplicate(Document)` 0개 / `duplicate(Layer)` 0개 / **activeDocument 복귀 후 99개**. → 복제 전후로 active 를 전환하고, 결과를 **개수로 검증**한다.
2. **래스터에 여백이 없으면 오프셋이 캔버스 경계에서 잘린다** — 아트 크기에 딱 맞춰 구웠더니 잉크가 닿은 변만 오프셋 0mm 가 됐다(좌 3.00·하 2.90 은 정상, 상 0.00·우 −0.35). 재단선이 **조용히 틀리게** 나온다. → 패널이 `offsetMm + 2mm` 를 여백으로 넘기고 origin 을 그만큼 보정.
3. **일러 DXF export 는 숨긴 레이어도 내보낸다** — 그림 레이어를 숨겨도 INSERT 6개가 그대로 남았다(1.19MB). → 임시 문서에 재단선만 복제해 굽는다(0.17MB, 칼선만).
4. **`selection` 은 live 다** — `documents.add()` 로 활성 문서가 바뀌면 참조가 무효해진다. → 문서 생성 **전에** 배열로 고정.

5. **재단선이 있는 상태에서 재실행하면 이전 칼선이 입력 잉크로 섞인다**(구멍 작업 중 발견) — 전체선택(`selectall`)은 `'재단선'` 레이어도 잡는다. 실측: 그 상태로 재실행하니 조각 255개가 전부 이어져 외곽 1개가 됐다. **오프셋을 바꿔 다시 뽑는 것은 실사용에서 흔한 조작**이라 반드시 걸러야 한다 → `mesCut_isCutItem()` 으로 `rasterize`·`selBounds`·`selectionInfo` 세 곳 모두 제외(표시와 처리 대상이 어긋나지 않게).

부수로 진단 도구도 2건 고쳤다: `probe-cut-file.mjs` 의 `.trim()` 이 latin1 로 읽은 **UTF-8 한글 끝 바이트 `0xA0` 를 NBSP 로 보고 잘라내** 레이어명이 깨졌고(`재단선`→`ì¬ë¨ì`), 돔보 판정이 간격(step) 비교라 **방향마크 60mm 가 끼면 오탐**이었다(격자 위치 비교로 교체).

### 6.9 P2 래스터 실루엣 완료 — **Image Trace 는 필요 없었다** (2026-07-31)

당초 설계는 "래스터는 일러 Image Trace 로 벡터화"였다. 실측해 보니 **이미 P1 파이프라인이 래스터화를 거치므로 트레이스가 불필요**했고, 진짜 문제는 다른 데 있었다.

| 입력 | alpha 마스크 | 흰배경 제거 마스크 | 결과 |
|---|---|---|---|
| 투명 배경 래스터 | 14.7% (별 모양) | 14.7% | alpha 로 충분 ✅ |
| **불투명 래스터(사진)** | **87.5% (사각형!)** | **14.7% (별 모양)** | alpha 로는 실루엣이 안 나온다 |

임베드 래스터는 대개 **불투명 사각형**이라 alpha 로 뜨면 bbox 와 같아진다. → **배경 판정**을 넣었다:
- UI `배경` = 자동 / 투명 배경 / 흰 배경 제거 (실루엣 모드에서만 의미)
- **자동** = 흰 배경 제거로 잉크가 30% 이상 줄면(`wN < aN*0.7`) 흰 배경이 넓다고 보고 전환
- ⚠️ 흰 배경 제거는 **흰색 그림도 함께 지운다** → 결과 메시지에 `배경: 흰 배경 제거 (자동) — 흰색 그림이 있으면 함께 지워집니다` 로 **항상 무엇을 썼는지 표시**한다. 사용자가 결과를 의심할 때 원인을 바로 알 수 있어야 한다.

**실동작 검증**: 일러에서 별을 불투명 래스터로 구운 뒤 실행 → 자동으로 흰배경 제거 채택, 래스터 사각 141.1×141.1mm → **칼선 106.2×101.5mm·앵커 28개**(사각형이면 4~8개) = 별 실루엣 정확 추출.
`cut:smoke` 4항목 추가(투명→alpha / 불투명→자동전환 / 사용자 지정 존중 / 결과가 사각형이 아님).

> Image Trace 는 **배경이 복잡한 사진**(그라데이션·풍경)에서만 필요하다. 그 경우는 디자이너가 일러에서 누끼를 딴 뒤 넘기는 게 품질·통제 면에서 낫다 — 지금 범위에서 제외한다.

### 6.8 P3 네스팅 확장 타당성 (2026-07-31 실측)

**현 구조(마스크 + EDT + 오프셋)를 그대로 써서 true-shape 네스팅이 된다.** 프로토타입으로 확인:

| 시나리오 | bbox 패킹 | true-shape | 절감 |
|---|---|---|---|
| 삼각형 20개 | 600px | **360px** | **40%** |
| 혼합(삼각·원·L) 18개 | 638px | 554px | 13% |

성능 3~75ms(600×900px 시트). 구조적 이점 3가지:

- **조각 간 gap 이 공짜** — 마스크를 `gap/2` 만큼 `offsetMask` 로 팽창시켜 배치하면 끝. 이미 있는 함수다.
- **충돌 판정이 픽셀 AND** — NFP(Minkowski) 구현이 불필요하다. `HANDOFF-irregular-nesting-spec.md` §4-6이 요구한 "R4 polygon 재정의"도 래스터 겹침 판정으로 대체된다.
- **구멍 안에 다른 조각을 넣는 것이 자동** — 마스크 기반이라 구멍이 그냥 빈 공간으로 인식된다(§4.5 구멍 추출과 같은 자산).

⚠️ 주의: 프로토타입에서 90° 회전을 넣으니 오히려 나빠졌다(360→380px). 탐욕 배치가 회전 선택을 잘못한 것으로 **더 나은 휴리스틱이 필요**하다. 실제 시트(122×207cm @1mm/px = 2.5M px)에서는 탐색 비용이 커져 bbox 사전 필터·스카이라인 등 최적화가 필요하다.

### 6.10 P3 네스팅 실용 버전 완료 (2026-07-31)

`js/nesting.js`(패널 정본, 전역 `MesCutNest`) + `scripts/cut/nest-bench.mjs`(하네스, `npm run cut:nest`).
칼선 파이프라인의 자산을 그대로 재사용한다 — **gap = 마스크를 `gap/2` 팽창**, **충돌 = 픽셀 AND**(NFP 불요).

**흐름**: 잠금 → `mesCut_nestBegin`(대상 확정) → `mesCut_rasterizeItem(i)` 반복 → gap 팽창 → `MesCutNest.nest()` → params(`S`/`I` 줄) → `mesCut_nestApply`(**새 문서**에 복제 배치). 원본 문서는 건드리지 않는다.

**★배치 전략 — "최적화"가 역효과였다.** 처음엔 스카이라인으로 후보를 줄였는데 실측에서 **더 느리고 더 나빴다**:

| 전략 | 사용 길이 | 시간 |
|---|---|---|
| 순수 bottom-left (입력 순서) | **360px** | **13ms** |
| 순수 bottom-left (큰 것 먼저) | 544px | — |
| 스카이라인 + 최고점 최소 기준 | 528px | 198ms |

스카이라인은 조각 폭 전체의 최고점에서 출발해 **오목한 틈을 놓치고**, 만회하려 파고들면 검사만 늘었다. → **순수 BL 로 되돌리고**, 정렬은 `입력 순서`·`큰 것 먼저` **둘 다 돌려 나은 쪽**을 쓴다(수십 ms라 굳이 하나만 고를 이유가 없다). "큰 것 먼저"가 정석인데 뒤집힌 이유 = 서로 맞물리게 만들어진 입력 순서를 정렬이 깨뜨리기 때문이다.

**하네스 결과**(gap 4px 포함):

| 케이스 | bbox | true-shape | 절감 |
|---|---|---|---|
| 삼각형 20개 | 600 | **360** | **40%** |
| 회전 없음 → 0/90/180/270 | 366 | **274** | 25% |
| 혼합(삼각·원·L) 18개 | 618 | 554 | 10.4% |
| 다중 시트(평판 600×400) | — | 2장·14/14·유실 0 | — |

판정 = 전수배치·**겹침 0**(배치 결과를 다시 찍어 독립 검증)·경계·절감(이형이 사각보다 나쁘면 실패)·다중시트.

**실동작 검증**: 삼각형 12개(위/아래 교대) → 롤 1370mm·gap 3mm·회전 허용 → **시트 1370×87mm에 12/12 배치, 아트보드 이탈 0, 여백 1.5mm(=gap/2) 정확**, 효율 47.5%.

> ⚠️ 실측 중 발견한 ExtendScript quirk: **비활성 문서의 `artboards` 를 읽으면 활성 문서 값이 나온다.** 사용자 파일까지 같은 크기로 보여 한참 헤맸다 — 문서 크기를 확인하려면 `app.activeDocument` 로 전환한 뒤 읽을 것.

### 6.12 표준 벤치마크 대조 (2026-07-31)

자체 케이스로는 "bbox 보다 낫다"까지만 알 수 있다. 이 분야에는 수십 년 누적된 공개 인스턴스와 **best-known 활용률**이 있으므로 그 옆에 세웠다.

- best-known 출처 = [arXiv 2509.13329](https://arxiv.org/html/2509.13329v2) Table 3

| 인스턴스 | 조각 | 활용률% | best-known% | 격차%p | **bbox 대비 절감%** | 초 |
|---|---|---|---|---|---|---|

**평균 격차 17.0%p · 미배치 0 · 전부 1.2초 이내.**

> 문헌 수치는 **연속 기하(NFP) + 수 분~수십 분 탐색** 결과다. 우리는 래스터 격자 + 초 단위 탐욕이라 직접 비교는 부당하다. 그래서 **bbox 대비 절감**을 나란히 둔다 — 실무에서 바뀌는 건 그 숫자다(표준 인스턴스에서도 **20~26% 절감**).

**튜닝 이력 — 무엇이 효과가 있었나(전부 실측)**

| 시도 | 평균 격차 | 판단 |
|---|---|---|
| 초기(단일 순서, step 4) | 21.7%p | — |
| **투입 순서 다양화**(결정적 4종 + 시드 셔플) | **18.0%p** | ✅ 채택 |
| tries 8 → 16 → 32 | 18.0 → 18.0 → 17.9%p | ❌ **순서는 이미 포화** — 늘려도 무의미 |
| step 3 → 2 → 1 | 18.0 → 17.2 → 16.4%p | ✅ step 이 실질 병목 |
| **2단계 정밀화**(성근 격자로 순서 선택 → 이긴 순서만 촘촘히) | **17.0%p · 3배 빠름** | ✅ 채택 |

해상도(scale)는 6→16 으로 올려도 55~56% 에서 **정체**했다 — 해상도가 아니라 배치 규칙의 한계다. 더 좁히려면 NFP·SA 같은 근본 변경이 필요하고, 그건 이 spec 범위를 넘는다.

자체 하네스도 함께 좋아졌다: 혼합 도형 절감 10.4% → **14.8%**, 회전 274 → 270px.

### 6.13 주문서 연동 완료 — N1~N4 (2026-07-31)

### 6.14 돔보 필수화 (2026-07-31, 용준님 지시)

### 6.15 ★등록 mode 정정 — `impose` 는 ia-editor 전용이다 (2026-07-31)

**`mode:'impose'` 로 보내면 주문서에 안 뜬다.** 코드가 그렇게 갈라 놓았다:

```js
orderForm/intake.js:81   mode: 'single,both'   // "모아찍기용은 ia-editor 담당이라 여기 뜨면
                                              //  주문 라인으로 불러올 수 없는 노이즈가 된다"(2026-07-28)
iaEditor.js:311          mode: 'impose,both'
```

`impose` = **"대지로 가져와 다시 배치할 조각"**. 재단 패널이 만드는 네스팅 시트는 **이미 배치가 끝난 완성 1건**이라 재배치 대상이 아니고 곧바로 주문 라인이 되어야 한다 → **`single`**.

- 정정 전: `id=93 mode=impose` → 주문서 피커에 **안 보임**(ia-editor 로만)
- 정정 후: `id=95 mode=single` → 주문서 필터(`single,both`)에 **잡힘** ✅

> 흡수(`absorb`)는 **주문서에만** 있다(`orderForm/intake.js:859`). 주문 저장 후 `ofIntakeAbsorbAll(orderId)` 이 라인에 마킹된 대기물을 `absorbed` 로 바꾸고 `order_item_id` 를 링크한다.

### 6.17 ★역수출 — A0 묶음분리를 잉크 실루엣으로 교체 (2026-07-31, 용준님 지시)

재단 패널에서 검증된 실루엣을 **A0 패널로 되가져왔다**. 재단이 아니라 **묶음분리·자동감지**가 대상이다.

**문제**: 세 엔진이 조각을 아는 방식이 달랐다.

| | 조각을 무엇으로 아는가 | 겹침 판정 |
|---|---|---|
| ia-editor 모아찍기 | `{id,w,h}` — **숫자 2개** (`iaEditor.js:1805`) | 자유사각 (MaxRects) |
| A0 묶음분리 (구) | bbox `[L,T,R,B]` (`mes-a0-host.jsx` `mesA0_cluster`) | 축정렬 사각 `ov()` |
| 재단 패널 | 픽셀 실루엣 | 픽셀 AND |

A0 는 **도형을 모른 채** 사각으로만 묶었다. 비스듬히 놓인 디자인은 잉크가 떨어져 있어도 bbox 가 겹쳐 한 덩어리가 됐고, 완화책이 두 번(클립 존중 경계·음수 gap) 들어갔지만 근본 원인은 "사각으로 본다" 하나였다.

**구조** — 계산부를 패널에 두는 재단 패널과 동일(ExtendScript 는 테스트가 사실상 불가능하다):

```
[호스트] mesA0_seedBegin(source,gap)   후보 수집 → 임시문서 복제 → PNG 1장 (굽기는 1회뿐)
   ↓ path·w·h·ox·oy·mmpp·bounds[]
[패널]  inkMask → offsetMask(gap/2) → components → 아이템별 최다중첩 배정 → "0,3;1,2"
   ↓
[호스트] mesA0_seedApply(spec)          공간정렬 → 큐 적재 (정렬·인덱스는 호스트 단일 소스 유지)
```

- `gap` 의미 보존: 양수=이 거리 이내면 한 디자인(팽창) · 0=닿을 때만 · 음수=더 잘게(침식)
- 치수(`w`/`h`)는 **아이템 union bbox 그대로** — 재료 소요는 외곽 사각이 맞다. 묶음만 바로잡히면 치수는 자동으로 옳아진다(회귀 0)

**★잉크 판정 = `alpha` 이지 `white` 가 아니다** (2026-07-31 용준님 지적으로 정정)

재단 패널은 `inkMask(img,'white')` — 흰 픽셀을 **배경으로 버린다**. 흰 바탕 위 그림의 **외곽을 따는** 용도라 그게 맞다. 그러나 A0 분리는 "디자인이 어디에 있나"를 보는 것이므로 **흰색도 그림**이다. `white` 로 두면:

- 흰 글씨·흰 바탕 배너가 배경으로 사라져 **한 디자인이 여러 덩어리로 쪼개진다**
- 흰 요소로만 된 개체는 잉크 0(noink) → 제 디자인과 못 합쳐지고 단독 행이 된다

임시문서는 배경이 투명(`transparency=true`)이라 **alpha>0 = 아트가 있다** 가 정확한 판정이다. 회귀 = smoke `흰 조각도 잉크로 세어 한 디자인으로 묶임`(검정+흰 조각 맞닿은 개체 2개 → `0,1` 1건. `white` 로 되돌리면 `0;1` 2건으로 **실제로 깨지는 것을 확인**했다).

⚠️ 대가 = **전면을 덮는 배경 판**(흰 판·테두리)이 선택에 섞이면 전부 그것을 통해 이어져 1건이 된다. 조용히 틀리지 않도록 "개체는 N개인데 잉크가 전부 이어져 1건" 경고로 드러낸다. 실패가 **시끄러운 쪽**을 골랐다 — `white` 의 실패(행이 조용히 늘어남)는 그럴듯해 보여서 못 잡는다.

**★한계 2가지 (반드시 알고 쓸 것)**

1. **배정 단위는 개체다.** 선택이 그룹 1개면 잉크가 N덩어리로 보여도 **1행밖에 안 나온다**. 원인 판정은 **개체 사실(`grp`=그룹 개체 수)** 로 한다 — 처음엔 `comps>1`(잉크 덩어리 수)로 판정했는데 **틀린 접근**이었다: 흰 요소·투명 간격 때문에 한 디자인도 여러 덩어리로 보여 *엉뚱하게 "그룹을 푸세요"* 라고 말하게 된다. 그룹인지는 **파일이 아는 사실**이므로 호스트가 그대로 올려보낸다.
2. **분리 해상도 = `mmPerPx`.** 픽셀 상한(12M)에 맞춰 자동으로 거칠어지므로 그 이하로 붙은 디자인은 여전히 붙는다. 실제 값을 결과 메시지에 항상 표시하고, 1mm/px 초과면 경고한다.

**폴백** — 굽기 실패(캔버스 한도·export 오류) 시 옛 사각 방식으로 큐를 채우되 **⚠를 띄운다**. 조용히 옛 동작으로 돌아가는 것이 가장 나쁘다. `mesA0_cluster` 는 이 경로 전용으로만 남았다.

**⚠️ 배포 순서 함정** — 축2(Z: 호스트)는 **전 PC 즉시 반영**인데 축3·축4(껍데기)는 PC별 수동 설치라 반영이 늦다. 그 사이 구버전 `main.js` 가 `mesA0_queueAddBatch`/`mesA0_autoDetect` 를 부른다 → **호환 shim 을 호스트에 남겨 뒀다**(전 PC 설치 확인 후 제거). 지웠다면 설치가 안 끝난 PC 는 묶음분리가 통째로 죽는다.

**`geometry.js` 사본 2벌** — A0 는 재단 패널 것의 **바이트 동일 사본**을 갖는다. Node 하네스(`cut:bench`·`cut:nest`)가 **재단 패널 파일을** 로드해 검증하므로, 사본이 갈라지면 "검증한 코드 = 배포된 코드" 등식이 조용히 깨진다(A0 쪽은 검증된 적 없는 코드가 도는데 하네스는 계속 통과). → `audit:ia-jsx` 에 **repo 사본 일치 검사**를 추가했다(축 비교는 repo↔런타임만 보므로 이건 그물에 안 걸렸다).

**검증** (`panel:smoke` 103→112):
- bbox 겹침 + 잉크 분리 → **2건 분리**, 배정 `0;1` ← 이번 변경이 고치려던 것
- 잉크 2덩어리 + 개체 1개 → 1건 + "개체가 1개" 진단 ← 실루엣이어도 못 고치는 것
- 굽기 실패 → 큐는 채워지되 "사각(bbox) 방식" 경고 ← 폴백이 조용하지 않은가

스모크가 마스크를 흉내내지 않고 **캔버스로 진짜 PNG 를 만들어** 넘기므로 `inkMask→components→배정` 경로가 헤드리스에서 그대로 돈다.

### 6.20 ★간격이 요청보다 좁게 나갔다 — 해상도 스냅으로 근본 제거 (2026-07-31, 용준님 보고)

**"간격 3mm 인데 개체 사이 최근접이 3mm가 안 된다"** — 실재 결함이었고 원인은 배치가 아니라 **해상도**였다.

`offsetMask` 는 `dist <= r` 로 판정하는데 축방향 거리는 정수라 **r 의 소수부가 통째로 버려진다**:

| 요청 | 해상도 | r(px) | 실팽창 | 보장 간격 |
|---|---|---|---|---|
| 3mm | **1.0mm/px** | 1.5 | **1px** | **2.00mm ★1mm 부족** |
| 5mm | 1.0mm/px | 2.5 | 2px | **4.00mm ★1mm 부족** |
| 3mm | 0.75mm/px | 2 | 2px | 3.00mm ✅ |
| 2·4·10mm | 1.0mm/px | 정수 | — | 정확 ✅ |

`pickResolution` 이 **롤 1370·1520 에만 1.0mm/px** 를 주므로(914·평판은 0.5) **기본 시트 + 간격 3mm 가 정확히 최악 조합**이었다. `gap/2` 가 픽셀 정수배인 2·4·10mm 는 멀쩡해서 "가끔 맞는다"로 보였다.

→ **`snapResolution(mmpp, gap, W, H, maxPx)`** 신설: `gap/2` 가 정수 px 이 되는 해상도로 내린다(3mm@1370 → **0.75mm/px · r=2px**). 비용이 상한을 넘으면 팽창 픽셀을 줄이고, k=1 로도 안 되면 **올림으로 폴백**(`exact=false`)해 절대 부족하지 않게 한다.

- **★예산은 `pickResolution` 것을 쓰면 안 된다** — 12M 상한은 EDT(Float32 4바이트) 비용에서 나온 값인데 네스팅 시트 버퍼는 `Uint8Array`(1바이트/칸)다. 그대로 쓰면 0.75 대신 **1.5mm/px** 로 떨어져 칼선이 더 각져진다(실제로 그렇게 나왔다). → `NEST_MAX_PX = 24e6` 별도.
- 조각 좌표 보정도 `gap/2` 가 아니라 **실제 팽창량(`rPx × mmpp`)** 으로 바꿨다. 둘이 다를 수 있다.
- 결과 메시지에 **실보장 간격을 항상 표시**한다 — 조용히 좁게 나가는 게 이 결함의 본질이었다.

### 6.22 효율% 교정 · 폭 추천 (2026-07-31)

**효율%는 표시되고 있었는데 값이 틀렸다**(§6.19 의 "표시하지 않을 뿐"은 오기). 분자가 **gap 팽창된** 잉크, 분모가 **usable**(돔보 여백 제외)이라 양쪽 다 과대 — 실측 **60.0% 표시 ↔ 실제 35.6%(1.7배)**.

→ 분자 = **팽창 전** 잉크(굽는 시점에 따로 센다) · 분모 = **실제 소요 재료**(폭 전체 × (사용 길이 + 돔보 여백)). 재료비 기준이라 여백을 뺄 수 없다.

**[폭 추천]** = 롤 5종(914·1050·1270·1370·1520)을 훑어 **사용 면적이 가장 작은 폭**을 고른다.

- **조각은 한 번만 굽는다** — 래스터는 폭과 무관하다. 해상도도 **가장 넓은 후보 기준으로 한 번** 정한다(폭마다 다르면 비교가 성립하지 않는다).
- 비교 지표는 효율%가 아니라 **면적(폭 × 소요길이)** — 좁은 롤이 효율은 높은데 길이를 더 먹는 경우가 갈린다. 실측에서 실제로 갈렸다(조각 20개: 1270 이 106mm 로 가장 짧은데 면적은 914 가 최소).
- 실소요 = **5폭 218~342ms**(성근 `tries:2`). 진행 표시만 두고 별도 UI 는 불필요.

### 6.23 ★실사용 재현 — 재단선이 구부러진 진짜 원인 (2026-07-31, 용준님 보고 · MCP/CDP 실측)

### 6.24 조각 칼선을 미세 마스크에서 (2026-07-31)

**칼선을 배치 격자(거친)에서 뽑으면 윤곽이 격자 한 칸(0.75mm) 단위로 뭉툭해진다.** 배치 좌표의 격자 오차는 **아트와 칼선이 함께 움직여 상쇄**되므로, 아트가 놓이는 자리를 기준으로만 놓으면 정확도가 미세 격자(0.25mm) 수준이 된다.

```
[보관]  조각마다 축소 전 미세 마스크 (예산 60M px 초과 시 그 조각만 거친 경로)
[칼선]  미세 마스크 팽창(rPx×sub) → 회전·trim → 컨투어
[정렬]  아트 잉크 원점(같은 회전 프레임의 trim 오프셋)을 빼서 **`I` 줄과 같은 식**에 얹는다
          baseX = pl.x*mmpp + rPx*mmpp + DOMBO   ← nestApply 가 아트를 놓는 바로 그 좌표
          x_mm  = baseX + (grownTrim.offX − artTrim.offX + px) × fineMmpp
```

**★거친 마스크 기준으로 놓으면 상쇄가 깨져 오히려 어긋난다** — 정밀해진 만큼 더 틀린다. 그래서 정렬 수식을 `cut:smoke` **3i** 로 고정했다(미세·거친 두 경로가 같은 자리인가 · 칼선이 아트−gap/2 인가 · 회전 90° 에서도 유지되는가 · 크기가 아트+gap 인가).

> 게이트가 실제로 무는지 확인했다 — `baseX` 에서 `rPx*mmpp` 를 빼 보니 **3건 FAIL**(96.5 vs 98.00), 되돌리니 88/88. 통과만 확인하고 넘어가면 "못 잡는 테스트"가 남는다.

> ⚠️ Illustrator MCP 는 이 세션 내내 **간단한 표현식 외에는 연결이 끊겼다**. 패널 CDP(8889) 로 `evalScript` 를 태우는 쪽이 안정적이다. 비활성 문서의 `pageItems` 를 훑으면 느려 타임아웃이 나므로 **`app.activeDocument` 로 전환한 뒤** 읽을 것.

### 6.25 ★여백·간격 분리 — 재단선 = 디자인 + 여백 (2026-08-01, 용준님 지시)

**"기본 디자인의 테두리 + 여백이 재단선이고, 재단선을 기준으로 여백이 다시 붙어야 한다."**

그때까지 두 값이 하나로 묶여 있었다 — `간격`이 **디자인↔디자인** 거리이고 칼선은 그 정확히 중간(간격/2)에 놓였다. 그래서 **인접 칼선이 맞닿았고**(사이 재료 0), 글자 도안에서 조각이 서로의 속으로 들어가 보인 것도 같은 뿌리다.

```
(구) [디자인] ←──── 간격 ────→ [디자인]      칼선은 중간 → 칼선끼리 0mm
(신) [디자인] ←여백→ ‖칼선‖ ←── 간격 ──→ ‖칼선‖ ←여백→ [디자인]
     디자인 사이 = 여백×2 + 간격
```

| 값 | 의미 | 범위 |
|---|---|---|
| **여백** | 디자인 → 칼선 | **음수 허용** |
| **간격** | 칼선 ↔ 칼선 | 0 이상 |

- **여백 0** = 칼선을 디자인 경계에 (실사용 사례)
- **여백 음수** = 도련이 이미 들어간 아트 — 칼선이 **잉크 안쪽**에 놓여야 한다(도련 2mm → 여백 −2). `insetMask` 로 처리.
- 배치 마스크 = `여백 + 간격/2` 팽창 · 칼선 = `여백`만 팽창 → 두 값이 독립한다.
- 칼선 반경(미세 px)은 **내림** — 칼선이 잉크 쪽으로 조금 더 붙어야 간격이 부족해지지 않는다.

**★안전 여유 = 격자 반 칸** (실측으로 확정). 배치는 **거친 격자** 마스크로 겹침을 막고 칼선은 **미세 격자** 마스크에서 뽑으므로, 두 마스크가 최대 `mmpp/2` 어긋나 그만큼이 칼선 간격에서 깎인다.

| | 여백3·간격5 실측 |
|---|---|
| 안전 여유 없이 | 칼선 간격 **4.33mm** (= 5 − mmpp 0.92 와 일치) ❌ |
| 여유 = mmpp/2 + fine | 4.50~4.81 보장이나 **1.5mm 과다** |
| **여유 = mmpp/2** | 칼선 간격 **5.53mm** ✅ · 과다 0.53mm |

### 6.26 실루엣 추출 두 경로 계측 — 벡터 vs 래스터 (2026-08-01)

**질문**: 실루엣은 파일 안에 이미 정확한 벡터로 있는데, 현행은 그걸 **렌더 → 임계 → 픽셀 계단 → 곡선 피팅으로 복원**한다. 이 왕복이 실제로 손해인가?

도구 = `mesCut_selectionPaths()`(호스트, 좌표를 mm·y-up 텍스트로) + `flattenSubpath`/`fillPolygonsInto`(geometry.js) + `npm 없이` `node scripts/cut/vector-vs-raster.mjs`. **같은 격자·같은 원점**에서만 비교가 성립한다.

★**불리언 union 을 만들지 않는다** — 여러 폴리곤을 같은 마스크에 그리면 그게 합집합이고, compound path 구멍은 서브패스를 **한 번에** 넘겨 even-odd 로 뚫는다.

**① 면이 채워진 아트**(타원 100×60 + 별 R45/r18 + 도넛 ⌀80/⌀40 · 0.25mm/px)

도형별 분해(정정 후):

| 도형 | 벡터 | 래스터 | 차 | 함의 밴드폭 |
|---|---|---|---|---|
| 별 | 23.81 | 23.97 | **+0.7%** | 0.052mm |
| 타원 | 47.14 | 47.28 | **+0.3%** | 0.058mm |
| 도넛(결함) | 37.71 | 50.43 | +33.7% | 3.373mm |

**★원인 = `polarity`(패스 방향).** 같은 도넛을 두 방식으로 만들어 대조:

| 생성 방식 | polarity | 벡터 | 래스터 | 차 |
|---|---|---|---|---|
| `Object > Compound Path > Make` (디자이너 방식) | `-+` | 37.71 | 37.93 | **+0.6%** ✅ |
| `compoundPathItems.add()` + 자식 추가 | `++` | 37.71 | **50.44** | +33.8% ❌ |

**⇒ 정정된 결론: 제대로 만든 아트에서는 래스터와 벡터가 0.3~0.7% 이내로 일치한다**(밴드 0.05~0.06mm = 격자의 1/4). **정확도에서 벡터의 이득은 사실상 없다.**

**⇒ 벡터 리더가 지켜야 할 것**: even-odd 를 무조건 적용하면 안 된다. `pathItem.polarity` 를 읽어 **일러가 실제로 렌더하는 채우기 규칙을 재현**해야 한다(`mesCut_selectionPaths` 에 polarity 미포함 — 채택 시 추가 필요).

**② 이미 칼선인 파일**(시트컷 실도안 글자 18조각 · 서브패스 20 · 앵커 1117 · 곡선핸들 91%)

| | 면적 | 섬 | 의미 |
|---|---|---|---|
| 래스터 | 46.0cm² | **20** | **획(0.35mm 선)만** 잉크로 봄 |
| 벡터 `--fill-closed` | **1769.0cm²** | **18** | 글자 몸통 = 자를 대상 |

`filled 0 / stroked 18` — 렌더는 선만 보여주니 §6.23 의 "효율 1.1%·조각이 서로의 속으로" 가 여기서 나온다. 섬도 20 vs **18**(조각 수와 정확히 일치)로 갈린다.
→ **닫힌 패스를 면으로 간주**하는 판단은 벡터 좌표가 있어야만 할 수 있다. 래스터로는 원리적으로 불가능하다.

**결론 (정정 후)** — **벡터 전면 전환은 근거가 약하다.**

| | 벡터의 이득 |
|---|---|
| 정확도 | **거의 없음** (0.3~0.7% · 밴드 0.05mm — 물리 공차 ±0.5mm 보다 한참 작다) |
| **면 없는 선** | **큼** — 래스터로는 **원리적으로 불가능**한 판단(46 → 1769cm² · 섬 20 → 18) |
| 비용 | 텍스트 파일 vs 8.5M px PNG 굽기 — 벡터가 훨씬 쌈 |

그리고 벡터는 **새 위험을 들여온다** — polarity·투명도·효과·오버프린트 등 "일러가 실제로 렌더하는 것"을 우리가 재현해야 한다. 래스터는 그걸 공짜로 얻는다. 위 도넛이 그 위험이 실제로 문 사례다.

→ **범위를 좁힌 제안**:
- **(가) 채택 권장**: 좌표는 **판정에만** 쓴다 — `filled 0 && stroked>0 && 닫힘` 이면 "이미 칼선인 파일"로 보고 **경고 + [닫힌 패스를 면으로] 옵션**. 마스크는 계속 래스터. §6.23 의 "효율 1.1%·조각이 서로의 속으로" 가 이걸로 해소된다. 위험 낮고 이득이 명확하다.
- **(나) 보류**: 벡터 마스크 전면 채택. polarity·투명도 재현 부담 대비 정확도 이득이 없다.

**그대로인 것**: 오프셋은 EDT라 라운드 조인 고정(§9-3) · 큰 아트 픽셀 예산.

2. `applyEffect` 뒤 **선택을 다시 지정**하지 않으면 `expandStyle` 이 조용히 안 먹는다 — bbox 가 원본 그대로라 **성공처럼 보인다**
3. **재합집합 필수** — Offset Path 는 자기교차 고리를 남긴다(그게 벡터판 '선 중복')
4. 클립 그룹에 그냥 합집합을 걸면 **클립이 무시된다**(실측: 클립 60×60 인데 실루엣 200×100) → `Live Pathfinder Crop` 을 **클립 그룹에만** 건다
5. **★조인 타입 상수가 UI 순서와 다르다.** 별(뾰족 끝 반각 19.2°)에 3mm 를 걸어 폭 증가를 재면 `jntp=0` **+6.000(라운드)** · `1` +3.447(팁이 잘린다) · `2` +16.529(마이터). **사각·원으로는 셋이 구별되지 않는다**(90° 코너는 bbox 가 같다) → 뾰족 도형으로만 잡힌다. 처음엔 1을 라운드로 알고 넣었고 사각 테스트는 통과했다.
6. **선 도안은 벡터에서도 채워야 한다** — 안 채우면 `선 아웃라인`이 **획만** 면으로 바꿔 실루엣이 아니라 고리가 나온다(실측 70×50 선도안: 채움 → 단일 76.35×56.35 ✅ / 안 채움 → 76.35 고리 + 63.65 구멍 ❌). 판정은 래스터와 **같은 `mesCut_artKind`·같은 규칙**을 쓴다(`mesCut_fillClosedItem` 로 정본 하나).
7. **`layers.add()` 는 새 레이어를 활성 레이어로 만든다** — 그대로 두면 칼선을 한 번 만든 뒤 **사용자가 그리는 그림이 전부 재단선 레이어로 들어간다**. `ensureCutLayer` 에서 되돌려도 메뉴 명령(group·expandStyle)이 다시 활성화하므로 **끝에서 한 번 더** 되돌린다.

> ⚠️ **정정** — 처음엔 "블록을 못 읽는 재단기에는 칼선이 없는 파일로 보인다"고 적었으나 **근거가 틀렸다**. 사내 실물 생산 DXF(2026-07-31, 포맥스5T)를 뜯어보니 **그쪽도 BLOCK + INSERT 구조**다(§2.5). 즉 우리 CNC 는 블록을 읽는다. 평평한 ENTITIES 가 더 호환적인 것은 맞지만 **이 수정이 없었다면 못 잘랐을 것이라는 말은 사실이 아니다.**

DXF 자체는 정상이다: 단위 `INSUNITS=4`(mm) · 레이어 `재단선` 하나 · 곡선은 SPLINE 으로 보존.

### 6.19 효율 %·추천 폭 (착수 전 점검 — ✅ §6.22 로 구현 완료)

**효율 %** = 이미 계산돼 있다. `nesting.js:263` 이 `efficiency: totalInk/totalArea` 를 반환하는데 **패널이 표시하지 않을 뿐**이다. 다만 그대로 쓰면 안 된다:
- `totalInk` 는 **gap 팽창된** 마스크 픽셀 수다(조각을 `offsetMask(gap/2)` 한 뒤 넣으므로) → 실면적보다 크게 나온다. 조각이 작고 gap 이 클수록 과대.
- `totalArea` 는 **usable 영역**(돔보 여백 제외) 기준이다 → 재료비 기준이라면 분모는 실제 시트(`폭 × 소요길이`, 여백 포함)여야 한다.
→ 팽창 전 잉크 수를 따로 보관하고, 분모는 mm 기준 실제 시트로 계산할 것.

**추천 폭** = 가능하다. `nest(pieces, opts)` 가 `opts.tries`·`opts.step` 을 받으므로 **성근 스캔(tries 2)** 으로 후보 폭 5종(914·1050·1270·1370·1520)을 훑고 **이긴 폭만 정밀 재실행**하면 된다(2단계 구조가 이미 그 모양이다). 조각 래스터는 폭과 무관하므로 **다시 굽지 않아도 된다** — 스캔 비용은 순수 배치 계산뿐.
- 비교 지표는 효율%가 아니라 **사용 면적(폭 × 소요길이)** 이어야 한다. 좁은 롤이 효율은 높은데 길이를 더 먹는 경우가 갈린다.
- 폭이 좁을수록 돔보 여백(23×2mm)이 상대적으로 커진다 — usable 폭으로 비교할 것.
- 조각이 usable 폭보다 넓은 후보는 제외.
- **미측정** = 5폭 스캔 실소요 시간. 착수 시 하네스로 먼저 재고 UI 를 정할 것(동기 계산이라 초 단위면 진행 표시가 필요하다).

### 6.11 `/ia-editor` 통합 경로 (설계만)

`nesting.js`·`geometry.js` 는 **의존성 0 순수 JS**라 웹에서도 그대로 돈다. 통합 시 고려할 것:

| 항목 | 상태 |
|---|---|
| 배치 엔진 | 그대로 이식 가능(`<script>` 또는 `?raw` 인라인) |
| 출력 계약 | 재단 패널의 `S`/`I` 줄 ↔ ia-editor `placements[{group_index,x_cm,y_cm,width_cm,height_cm,rotated,rotation}]` — **true-shape 배치도 bbox+rotation 으로 표현 가능**하므로 계약 변경 불요(§4.3 회전 실측) |
| **마스크 조달** ★ | 웹이 가진 건 썸네일이고 **알파가 없다**([[design-irregular-nesting]]) → 웹 단독으로는 true-shape 를 못 한다. **패널이 만든 마스크/폴리곤을 API 로 올리는 경로**가 필요하다 |
| 기존 패커 | `iaeMaxRectsPack`(bbox) 는 **그대로 둔다** — 회귀 0 원칙(§8). true-shape 는 옵션 분기로 |

⇒ 통합의 병목은 엔진이 아니라 **마스크 조달**이다. 패널에서 칼선을 만들 때 폴리곤을 함께 저장해 두면 웹이 그것을 받아 배치만 하면 된다.
