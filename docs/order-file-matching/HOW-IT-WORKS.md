# 이게 어떻게 돌아가는가 — 처음 보는 사람을 위한 설명

> 기술 용어를 최대한 줄였습니다. 자세한 수치·근거는 `README.md`에 있습니다.

---

## 1. 지금 회사는 이렇게 일하고 있습니다

```
주문 전화·카톡 접수
      ↓
이카운트에 주문서 입력            ← 경리
      ↓
Z: 공유폴더에 작업파일 저장        ← 디자이너
   (2026년\08월\11일\27-거래처-…\)
      ↓
출력 → 완료 폴더로 파일 이동       ← 오퍼레이터
      ↓
출고 → 이카운트에 판매 입력        ← 경리
```

**핵심은 순서입니다.** 이카운트 주문서가 **먼저** 만들어지고, 파일이 **나중**에 생깁니다.
파일은 주문의 결과물이지 출발점이 아닙니다.

---

## 2. MES로 옮기면 순서가 뒤집힙니다

MES를 쓰기 시작하면 이카운트 주문서가 없어집니다. 그러면 주문 정보는 어디서 올까요?

> **파일 이름이 곧 주문서입니다.**

실제 파일 이름을 뜯어보면 이렇습니다:

```
27-(솔벤현수막)연안애드마트-농협공판장(506x92-1장)사방접어미싱_13일 오전직배.eps
│  │            │           │        │           │            └ 언제·어떻게 보낼지
│  │            │           │        │           └ 후가공
│  │            │           │        └ 크기와 수량
│  │            │           └ 현장 이름
│  │            └ 거래처
│  └ 무엇으로 만드는지
└ 그날 몇 번째 주문인지
```

주문서 한 줄을 채우는 데 필요한 게 **거의 다 들어 있습니다.**
실측하면 거래처 87%, 크기 87%, 수량 80%가 파일 이름만으로 읽힙니다.

## 3. 그래서 만든 것

```
Z: 폴더 스캔  →  이름 해석  →  MES 「가공대기함」에 쌓기  →  사람이 확인  →  주문서  →  카드
   (자동)        (자동)          (자동)                    ★여기만 사람     (자동)    (자동)
```

**가공대기함**은 원래 있던 화면입니다. 디자이너가 일러스트레이터에서 작업하면 자동으로 여기 쌓이고,
경리·관리자가 확인해서 주문서로 만드는 구조가 **이미 운영 중**이었습니다.

우리가 새로 만든 건 **입구 하나**뿐입니다 — 이미 Z:에 쌓여 있는 파일들을 대기함에 올리는 길.

```bash
# 1) 썸네일(미리보기 그림) 뽑기
python scripts/zscan-thumb.py --from 2026-08-01 --to 2026-08-11 --out thumbs.jsonl

# 2) 대기함에 올리기 (--commit 없으면 미리보기만)
node scripts/zscan-intake.cjs --from 2026-08-01 --to 2026-08-11 --thumbs thumbs.jsonl --commit
```

## 4. 카드는 어떻게 만들어지나

**카드 = 생산 현장이 보는 작업 지시**입니다. 주문서 한 줄이 카드 한 장이 됩니다.

```
가공대기함 항목            주문서 한 줄               카드 한 장
──────────────           ──────────────            ──────────────
거래처: 연안애드마트    →   거래처                →    거래처
품목:  솔벤 현수막      →   품목                 →    품목
크기:  506×92cm        →   규격                 →    규격
수량:  1장             →   수량                 →    수량
그림:  (썸네일)         →   (자동으로 따라감)      →    ★그림이 보임
파일:  Z:\…\27-….eps   →   (자동으로 따라감)      →    출력할 파일
```

카드가 만들어지는 순간은 **주문서를 저장할 때**입니다. 따로 만들 필요가 없습니다.

### 그림(썸네일)은 어떻게 따라가나

이 부분이 좀 신기한데, **일러스트레이터를 켜지 않고** 그림을 뽑습니다.

EPS 파일 안에는 원래 **미리보기 그림이 통째로 들어 있습니다.** (윈도우 탐색기에서 파일을 미리 볼 수
있는 이유가 이것입니다.) 그 부분만 잘라내서 작게 줄이면 끝입니다.

- 검사해보니 3개 폴더의 EPS **100%가** 미리보기를 갖고 있었습니다
- 파일 하나당 24KB 정도로 줄여서 저장합니다
- 118개 전부 성공, 빈 그림 0개

한 번 올려두면 **주문서 → 카드로 자동으로 따라갑니다.** 새로 만든 코드가 없습니다.

### 카드가 완료 처리되는 방식

출력이 끝나면 장비 옆 컴퓨터가 MES에 알려줍니다. 그때 파일 이름으로 어느 카드인지 찾습니다.

> 그래서 **기존 파일 이름을 바꿀 필요가 없습니다.** 이미 파일 이름으로 직접 찾는 기능이 있습니다.
> 이름을 바꾸면 오히려 매칭이 깨집니다.

## 5. 이카운트는 앞으로 어떻게 되나

가장 헷갈리기 쉬운 부분입니다. **이카운트와 MES를 실시간으로 연결하지 않았습니다.**

### 이카운트는 「정답지」로만 썼습니다

시험 문제를 풀고 답을 맞춰보는 것과 같습니다.

```
Z: 파일에서 주문서를 만들어 본다        ← 우리가 푼 답
이카운트에 실제로 있는 주문과 비교한다   ← 정답지
얼마나 맞았나 센다                    ← 채점
```

7개월치(파일 4,611개, 주문 1,567건)를 이렇게 채점했습니다.
**실시간 연결도, 프로그램 연동도 쓰지 않았습니다.** 엑셀 한 번 내려받아서 대조했을 뿐입니다.

### 왜 연동하지 않나

| | |
|---|---|
| **연동하면?** | 이카운트에 계속 의존하게 됩니다. MES로 넘어가는 게 목적인데 반대로 갑니다 |
| **정답지로만 쓰면?** | 지금은 검증에 쓰고, MES가 자리 잡으면 그냥 안 쓰면 됩니다 |

그리고 결정적인 이유가 하나 더 있습니다.

### 「몇 번 전표인지 맞히기」는 곧 사라질 문제입니다

채점을 해보니 **파일 그룹이 이카운트 몇 번 전표인지 맞히는 정확도가 76~77%에서 더 안 올라갔습니다.**
날짜 범위, 점수 기준, 폴더 묶는 방식을 다 바꿔봤지만 그 자리였습니다.

처음엔 문제라고 봤는데, 다시 보니 **재고 있는 문제가 아니었습니다.**

- 지금은 이카운트 주문이 먼저라서 「이 파일이 몇 번 전표인가」를 되짚어야 합니다
- MES로 넘어가면 **이카운트 주문 자체가 없습니다.** 파일이 곧 주문입니다
- 즉 이 문제는 **전환하면 없어집니다**

실제로 확인해보니, 전표를 못 찾은 파일들도 **주문서를 채울 정보는 똑같이 다 갖고 있었습니다.**

| | 거래처 정보 | 크기 정보 | 수량 정보 |
|---|---|---|---|
| 전표를 찾은 것 | 90.2% | 98.4% | 90.7% |
| **전표를 못 찾은 것** | **92.4%** | **97.9%** | **92.7%** |

차이가 없습니다. 못 찾은 건 **정보가 없어서가 아니라 짝을 못 지은 것**뿐입니다.

> **결론**: 「전부 맞추기」를 목표로 삼지 않습니다. 24%는 영원히 안 맞습니다.

### 그런데 안 맞는 것 자체가 쓸모가 있습니다

처음엔 안 맞는 걸 그냥 오차로 봤는데, 다시 보니 **거기에 정보가 있었습니다.**

| 안 맞는 모양 | 뜻할 수 있는 것 |
|---|---|
| 파일은 있는데 이카운트에 주문이 없다 | **청구를 빠뜨렸을 수 있습니다. 실제로 못 받은 돈입니다** |
| 이카운트에 주문은 있는데 파일이 없다 | 깃대·국기봉 같은 부속품 판매(정상)거나, 파일을 안 만든 것 |
| 붙었는데 수량이 다르다 | 더 만들었거나 덜 청구했을 수 있습니다 |

그래서 **대사(맞춰보기) 도구**를 만들었습니다.

```bash
npm run zscan:recon -- --from 2026-07-01 --to 2026-08-11
```

7~8월치를 돌려보니 **청구 누락 후보 131건**, **파일 없는 출력물 주문 282건(7,801만원)**이 나왔습니다.

> ⚠️ **「후보」이지 「확정」이 아닙니다.** 예를 들어 금액 1위였던 `광고월드 어구실명제 2,173만원`은
> 파일이 실제로 있는데 규격 표기가 달라 못 붙은 것이었습니다. 사람이 확인해야 합니다.

이게 **이카운트를 병행해서 쓰는 이유**입니다. 나중에 MES만 쓰게 되면 비교 대상이 없어지지만,
지금 병행하는 동안에는 서로가 서로를 검사해줍니다.

## 6. 사람은 얼마나 손대야 하나

하루 평균 51건 기준입니다.

| 할 일 | 비율 | 하루 |
|---|---|---|
| **확인만 하고 넘어감** | 46.5% | 24건 |
| 거래처를 새로 등록하거나 골라줌 | 24.1% | 12건 |
| 여러 항목을 손으로 입력 | 22.3% | 11건 |
| 나머지 | 7.0% | 4건 |

**거래처 등록 24%는 한 번만 하면 됩니다.** 한 번 등록해두면 다음부터는 자동입니다.
시간이 지날수록 「확인만」 비율이 올라갑니다.

### 자동으로 확정하지 않는 이유

파일 그룹의 7.3%는 **이카운트에 대응하는 주문이 아예 없었습니다.** 재출력·수정본·샘플입니다.
이런 걸 자동으로 주문서로 만들면 **매출이 부풀려집니다.**

그래서 항상 `대기` 상태로만 쌓고, 사람이 확인해야 주문서가 됩니다.
읽지 못한 파일도 버리지 않고 올립니다 — **조용히 사라지는 게 제일 위험합니다.**

## 부록 — 용어

| 말 | 뜻 |
|---|---|
| **가공대기함** | 작업 파일이 주문서가 되기 전에 대기하는 곳. MES 안의 화면 |
| **카드** | 생산 현장이 보는 작업 지시 한 장. 주문서 한 줄 = 카드 한 장 |
| **정답지** | 이카운트에서 내려받은 실제 주문 내역. 채점 기준으로만 씀 |
| **썸네일** | 작은 미리보기 그림 |
| **제품유형** | 파일 이름 앞 괄호 안의 말. `(솔벤현수막)` |
| **후가공** | 출력 후 처리. 미싱·펀칭·재단 등 |
| **전사** | 천에 열로 찍어내는 방식. 태극기·깃발·가로등배너가 여기 |
