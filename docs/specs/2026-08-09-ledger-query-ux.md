# 원장 탭별 조회 UX 설계 (2026-08-09)

> 배경: 목록 UX 감사(`docs/audits/2026-08-08-list-ux-ecount-gap.md`)에서 `/ledger` 를 "리포트 허브라 일괄 이식 대상이 아님"으로 분류하며 남긴 별도 설계 건.
> 상태: **설계만. 구현 미착수.**

## 0. 먼저, 앞선 감사의 기술을 정정한다

감사 문서와 커밋 메시지에 **"원장은 15개 탭"** 이라고 적었는데 **사실이 아니다.** `grep -c "ds-tab\|switchLedgerTab"` 이 탭 버튼이 아닌 문자열까지 세서 나온 수치였다.

**실제 탭은 3개**다: `sales`(매출) · `purchase`(매입) · `analysis`(분석).

이 정정이 설계를 바꾼다 — 15개였다면 "어디까지 손댈지"가 핵심 문제지만, 3개면 **전부 다뤄도 된다.** 다만 탭 안의 표가 9개라 그 구조가 진짜 문제다.

## 1. 조사로 드러난 구조

| 탭 | 표(`tbody`) | 성격 |
|---|---|---|
| **매출** `salesContent` | `integrityBody` · `clientsTableBody` | 정합성 점검 + **거래처별 채권 목록** |
| **매입** `purchaseContent` | `supplierTableBody` | **공급처별 채무 목록** |
| **분석** `analysisContent` | `profitMonthlyBody` · `profitClientBody` · `collectionPeriodBody` · `transactionsTableBody` · `collectionLogsBody` · `pTransactionsBody` | 월별손익·거래처손익·회수기간 **집계표 3** + 거래내역·수금이력·매입내역 **명세 3** |

즉 9개 표가 **성격이 셋으로 갈린다**:

| 부류 | 표 | 조회 UX 가 필요한가 |
|---|---|---|
| **A. 원장 목록** (거래처/공급처별 잔액) | `clientsTableBody` · `supplierTableBody` | **필요** — 매일 보는 화면이고 건수가 많다(거래처 2,787) |
| **B. 명세 목록** (드릴다운 상세) | `transactionsTableBody` · `collectionLogsBody` · `pTransactionsBody` | **부분** — 특정 거래처를 고른 뒤의 상세라 필터가 이미 좁다 |
| **C. 집계표** (월별·거래처별·회수기간) | `profitMonthlyBody` · `profitClientBody` · `collectionPeriodBody` | **불필요** — 행이 12행·상위 N행 수준. 칩·페이징·열선택이 과하다 |
| **D. 점검표** | `integrityBody` | **불필요** — 이상 항목만 뜨는 경고판 |

## 2. 핵심 설계 판단

### 2-1. A 부류에만 적용한다 (2개 표)

전부에 붙이면 12행짜리 집계표에 "페이지당 50건" 셀렉트가 달린다. **도구가 내용보다 커진다.**

| 대상 | 이유 |
|---|---|
| `clientsTableBody`(매출 채권) | 거래처 2,787건 모집단. 매일 조회. 검색·정렬·열선택 수요가 실재 |
| `supplierTableBody`(매입 채무) | 같음. AP 정본이라 금액 신뢰가 중요 |

B(명세)는 **칩만** 붙인다 — 지금도 "어느 거래처·어느 기간을 보고 있는지"가 화면에 안 적혀 있어 스크롤하면 맥락을 잃는다. 도구모음·합계는 붙이지 않는다.

C·D 는 손대지 않는다.

### 2-2. ★ 원장은 이미 합계행이 있다 — 합계 바를 겹쳐 달지 않는다

`tfoot` 합계행이 이미 있고 회계 담당이 그걸 기준으로 본다. 여기에 `ds-summary` 바를 또 붙이면 **같은 숫자가 두 곳에 뜨고, 둘이 다르면 어느 쪽이 맞는지 알 수 없다.**

대신 확인할 것: **`tfoot` 합계가 "조회조건 전체" 기준인지 "현재 페이지" 기준인지.** 페이지 기준이면 그게 실제 결함이다(주문 목록에서 잡은 것과 같은 문제). 구현 전 실측한다(§5).

- 전체 기준이면 → 그대로 두고 **범위 문구만** 추가("조회조건 전체 합계").
- 페이지 기준이면 → 전체 기준으로 고친다. 이게 이 설계에서 가장 값나가는 부분일 수 있다.

### 2-3. 조회조건 SSOT

`/api/ledger` 계열도 목록·카운트·CSV 가 갈려 있을 가능성이 높다(다른 6개 페이지가 전부 그랬다). **구현 전 확인**하고, 갈려 있으면 `buildLedgerFilter` 로 통합한다.

⚠️ 원장은 **법인간거래 제외**(memory `design-intercompany-ledger-relocation`)와 **AR 파생**(`deriveClientBalance`) 규칙이 걸려 있다. 이 조건들이 SSOT 안에 들어가야 하며, 빠지면 채권 금액이 통째로 달라진다. AP 는 `client_type` 필터 금지(memory `feedback-ap-client-type-filter` — 2회 재발).

### 2-4. 배치

탭 구조는 그대로. 각 탭의 해당 표 위에 칩·도구모음을 넣는다. 탭 전환 시 **해당 탭 최초 진입에만 1회 마운트**(표가 `hidden` 이면 열 선택이 `thead` 를 못 읽는다 — 입고·세금계산서·출고에서 반복된 함정).

## 5. 구현 전 실측 항목 (설계의 빈칸)

1. **`tfoot` 합계가 조회조건 전체 기준인가, 현재 페이지 기준인가** — §2-2. 이게 페이지 기준이면 우선순위가 올라간다.
2. **원장 목록에 페이징이 있는가** — `limit=100/500` 이 보이는데 페이지네이션 UI 가 없다. 상한에서 조용히 잘리고 있다면(감사 G10 과 같은 문제) 그것부터다.
3. **조회조건이 목록·카운트·CSV 에 복사돼 있는가** — 다른 6개 페이지가 전부 그랬다.
4. **법인간거래 제외·AR 파생 규칙이 어디에 걸려 있는가** — SSOT 로 옮길 때 빠뜨리면 금액이 달라진다.

## 6. 판단 보류

1. **매출/매입 탭에 기간 필터가 필요한가** — 채권·채무는 "현재 잔액"이라 기간 개념이 약하다. 발생 기간으로 좁히는 수요가 실제로 있는지 확인 필요.
2. **분석 탭 명세 표에 페이징이 필요한가** — 거래처 하나의 내역이라 대개 짧지만, 대형 거래처는 길 수 있다.
