## 2. 핵심 설계 판단

### 2-1. 새 엔드포인트를 만들지 않는다 — `/api/orders` 를 확장한다

출고 이력은 **주문의 한 단면**이다. 전용 엔드포인트를 만들면 조회조건이 또 두 벌이 되고, 이번 감사에서 계속 잡아온 바로 그 문제(카드≠목록, CSV≠화면)를 새로 만드는 셈이다.

`src/routes/orders/listFilter.ts`(이미 목록·카운트·통계·CSV가 공유하는 SSOT)에 **두 가지만 추가**한다.

```
ship_date_from / ship_date_to   -- 출고 기준일 범위
sort: ship_date_desc / ship_date_asc
```

이력 탭은 `status=SHIPPED` + `ship_date_*` 를 붙여 같은 엔드포인트를 호출한다. 합계 바·칩·도구모음·프리셋·열 선택은 **이미 만들어둔 자산을 그대로 재사용**한다(추가 구현 없음).

### 2-2. ★ 출고일 결측 1,420건을 어떻게 다룰 것인가 (이 설계의 핵심)

`shipped_at` 이 비어 있는 1,420건은 **전부 2026-07월**, 즉 가장 최근 달이다.

- 출고일 기준으로만 필터하면 → **7월이 통째로 안 보인다.** 최근 달을 못 보는 이력목록은 쓸모가 없다.
- `COALESCE(shipped_at, order_date)` 로 조용히 메우면 → 「출고일」 열의 14%가 실제로는 주문일이 된다. 집계가 **말없이 왜곡**된다. 이쪽이 더 나쁘다.

**채택: 대체하되 숨기지 않는다.**

| 요소 | 처리 |
|---|---|
| 기간 필터 | 기준일 = `COALESCE(o.shipped_at, o.order_date)`. 필터 라벨에 **"출고일(미기록분은 주문일)"** 명시 |
| 「출고일」 열 | `shipped_at` 이 있으면 그 값, 없으면 주문일 + **「주문일 대체」 배지** |
| 조건 칩 | 결측이 포함된 조회면 **경고 칩** — "출고일 미기록 N건 포함(주문일로 대체)" |
| 정렬 | `ship_date_desc` = `COALESCE(shipped_at, order_date) DESC, o.id DESC` (tie-break 필수) |

경고 칩의 건수는 응답 `summary.ship_date_missing` 으로 내려준다. 앞서 발주 합계 바에서 "공급가 미기재 건 포함"을 띄운 것과 같은 방식이다 — **숫자가 이상해 보이는 이유를 화면이 스스로 말하게 한다.**

> 근본 해결은 **7월 이관분 `shipped_at` 백필**이다(§6 선행 과제). 백필이 끝나면 위 대체 로직은 자동으로 조용해진다(결측 0 → 배지·경고 미표시). 백필 없이도 동작하도록 설계했다.

### 2-3. 배송방법 통일 — `직접배송` (D4)

같은 업무를 법인이 다르게 적어왔다. `직배`=동산(e1) · `직접배송`=선명(e2). **정본은 `직접배송`.**

⚠️ **`배송` 206건을 같이 묶으면 안 된다.** 그중 **189건이 기초채권 이월 전표**(`E1-OPEN-*`, 금액 1.8억·-1.5억 등)이고 `delivery_method='배송'` 은 이관 생성기가 넣은 무의미한 기본값이다. 합치면 **가짜 직접배송 실적 189건**이 생긴다.

| 대상 | 처리 |
|---|---|
| `직배` 1,027건 | → `직접배송` |
| `직접배송` 567건 | 그대로 (정본) |
| `배송` 중 기초채권 전표 189건 | → **NULL(미기재)**. 배송이 아니다 |
| `배송` 중 2026년 산발 17건 | → `직접배송` (실주문) |

코드에서 `직배` 는 표시 문자열이 아니라 **판정에 쓰이는 값**이라 함께 고쳐야 한다:

| 위치 | 내용 |
|---|---|
| `src/routes/clients.ts:963` | 거래처 배송방법 **검증 화이트리스트** — 통일값 반영 필요 |
| `src/routes/shipments.ts:346` | `OWN_DELIVERY = new Set(['직배','용차','퀵'])` — 합배송 후보 탐지 |
| `src/scripts/orderFormDist.js:76` | `DM_MAP.DIRECT = '직배'` |
| `src/pages/orders.ts` · `shipments.ts` | 필터 `<option>` · 섹션 라벨 |
| `src/scripts/shipments.js:51,55` | 이미 `직배`·`직접배송` 둘 다 처리 — 통일 후에도 안전(하위호환 유지 권장) |

**전환 순서**: ①코드가 두 값을 모두 받아들이는 상태 확인 → ②마이그레이션(UPDATE) → ③화이트리스트·기본값을 `직접배송` 으로 → ④`직배` 하위호환 코드는 남겨둔다(과거 데이터·외부 유입 대비).

### 2-4. 회계 전표성 주문 제외 (필수)

`status='SHIPPED'` 인 195건(5.4억)이 실제 출고가 아니다 — 기초채권 `E1-OPEN-*` 189건 + 법인간미러 `ICM-*` 6건.

- 이력 조회에서 **제외**한다. 제외 규칙은 `order_number` 접두 패턴이 아니라 **명시적 플래그가 정본이어야 한다**(명명 규칙 의존은 이관 규칙이 바뀌면 깨진다 — 발주 법인간거래에서 이미 겪은 함정).
- 현재 플래그가 없으므로 1단계는 접두 패턴으로 제외하되, **`orders` 에 `is_voucher`(회계 전표) 플래그를 두는 것을 후속 과제로** 남긴다. 이 플래그는 출고 이력뿐 아니라 실적·생산 집계 전반에 필요하다.
- 제외 건수를 조건 칩에 표기한다 — "회계 전표 195건 제외".

### 2-5. 합배송

`orders.consolidate_with_order_id` 로 묶인 건은 주문 목록과 **동일한 배지 로직을 재사용**한다(대표/자식 표기). 이력에서 묶음을 한 줄로 합치지 않는다 — 청구·실적은 주문 단위가 정본이고, 합치면 금액 합계가 주문 목록과 어긋난다.

### 2-6. 반품 (D5)

**원칙: 출고 행은 그대로 두고, 반품 사실을 드러내되 상계하지 않는다.**

"이 기간에 얼마나 나갔나"(gross)와 "얼마가 남았나"(net)는 다른 질문이다. 반품을 음수 행으로 넣어 합계에서 빼면 출고량을 못 보고, 무시하면 되돌아온 건을 실적으로 센다. **한 숫자로 합치면 어느 쪽도 못 본다.**

2단계에서 붙일 형태:

| 요소 | 처리 |
|---|---|
| 행 | 「반품」 배지. 부분반품이면 수량 표기(`반품 3/10`) |
| 합계 바 | `반품 N건 / -금액` 을 **별도 항목**으로. 출고 합계에서 차감하지 않는다 |
| 필터 | 반품 **포함 / 제외 / 반품만** 3택 |
| 소스 | `returns` + `return_items` (order_id 로 조인) |

**1단계에서는 넣지 않는다.** prod `returns`·`customer_claims` 가 **0건**이라 동작을 확인할 수 없다. 검증 못 하는 UI 를 먼저 만들면 코드만 늘고 맞는지 아무도 모른다 — `shipments` 0건 때문에 정본을 orders 로 바꾼 것과 같은 판단이다. 1단계 쿼리는 반품 조인이 나중에 얹힐 수 있는 형태로만 남긴다.

## 3. 화면 설계

### 탭 구성 (`/shipments`)

```
[택배사별 실행] [준비상태] [이력]      ← 3번째 탭 신설
```

이력 탭은 **탭 진입 시 1회 마운트**한다(표가 `hidden` 이면 도구모음이 붙지 않는다 — 입고·세금계산서에서 이미 겪은 함정).

| 검색 | — | 주문번호·거래처명·품목명 (기존 orders 검색 그대로) |

| 거래처 | 전체 | 기존 파라미터 재사용 |

| 열 | 원본 | 숨김 가능 |

| 출고일 | `COALESCE(shipped_at, order_date)` + 대체 배지 | ○ |

- **`exclude_vouchers` 를 옵트인으로** 했다. 기본 주문 목록의 동작을 바꾸지 않기 위해서다. `voucher_excluded` 카운트 조회도 이 플래그가 있을 때만 돈다 — 다른 페이지가 왕복 비용을 내지 않는다.

- **`getBillingStatusColor/Text` 는 orders.js 전용**이라 shipments 에서 부르면 ReferenceError 다 → 로컬 맵으로 대체.
- **「주문일 대체」 배지가 열 폭에 잘려 안 보였다.** 대체 사실을 드러내는 게 이 설계의 핵심인데 무의미해지므로 열을 158px 로 넓히고 그 셀만 `overflow: visible`.
