## 0. 조사로 드러난 사실 (설계 전제를 바꾼 것)

| 2 | 그런데 **호출처가 0건**이다 | `grep` 전수 — 어떤 화면도 호출하지 않음 | 죽은 엔드포인트 |

| 4 | 실제 출고 실적은 `orders` 에 있다 — `status='SHIPPED'` **10,073건** | remote 집계 | 데이터가 있는 쪽은 orders |
| 5 | **`shipped_at` NULL 1,420건이 전부 2026-07월분** | `GROUP BY substr(order_date,1,7)` → `2026-07=1420` (단일 그룹) | **출고일 기준으로만 만들면 가장 최근 달이 통째로 빈다** |

`shipments` 행 생성 경로(`ensureShipmentForOrder`)는 카드 출고완료·주문 상태전이에 걸려 있다. 0건인 이유는 **이관분이 그 경로를 타지 않았고, 마지막 주문일이 2026-07-31이라 그 뒤 신규 출고가 없기 때문**이다. 앞으로 쌓일 테이블이지 지금 비어 있는 게 버그는 아니다.

## 2. 핵심 설계 판단

### 2-1. 새 엔드포인트를 만들지 않는다 — `/api/orders` 를 확장한다

출고 이력은 **주문의 한 단면**이다. 전용 엔드포인트를 만들면 조회조건이 또 두 벌이 되고, 이번 감사에서 계속 잡아온 바로 그 문제(카드≠목록, CSV≠화면)를 새로 만드는 셈이다.

`src/routes/orders/listFilter.ts`(이미 목록·카운트·통계·CSV가 공유하는 SSOT)에 **두 가지만 추가**한다.

```
ship_date_from / ship_date_to   -- 출고 기준일 범위
sort: ship_date_desc / ship_date_asc
```

이력 탭은 `status=SHIPPED` + `ship_date_*` 를 붙여 같은 엔드포인트를 호출한다. 합계 바·칩·도구모음·프리셋·열 선택은 **이미 만들어둔 자산을 그대로 재사용**한다(추가 구현 없음).

### 2-2. ★ 출고일 결측 1,420건을 어떻게 다룰 것인가 (이 설계의 핵심)

`shipped_at` 이 비어 있는 1,420건은 **전부 2026-07월**, 즉 가장 최근 달이다.

- 출고일 기준으로만 필터하면 → **7월이 통째로 안 보인다.** 최근 달을 못 보는 이력목록은 쓸모가 없다.
- `COALESCE(shipped_at, order_date)` 로 조용히 메우면 → 「출고일」 열의 14%가 실제로는 주문일이 된다. 집계가 **말없이 왜곡**된다. 이쪽이 더 나쁘다.

**채택: 대체하되 숨기지 않는다.**

| 요소 | 처리 |
|---|---|
| 기간 필터 | 기준일 = `COALESCE(o.shipped_at, o.order_date)`. 필터 라벨에 **"출고일(미기록분은 주문일)"** 명시 |
| 「출고일」 열 | `shipped_at` 이 있으면 그 값, 없으면 주문일 + **「주문일 대체」 배지** |
| 조건 칩 | 결측이 포함된 조회면 **경고 칩** — "출고일 미기록 N건 포함(주문일로 대체)" |
| 정렬 | `ship_date_desc` = `COALESCE(shipped_at, order_date) DESC, o.id DESC` (tie-break 필수) |

경고 칩의 건수는 응답 `summary.ship_date_missing` 으로 내려준다. 앞서 발주 합계 바에서 "공급가 미기재 건 포함"을 띄운 것과 같은 방식이다 — **숫자가 이상해 보이는 이유를 화면이 스스로 말하게 한다.**

> 근본 해결은 **7월 이관분 `shipped_at` 백필**이다(§6 선행 과제). 백필이 끝나면 위 대체 로직은 자동으로 조용해진다(결측 0 → 배지·경고 미표시). 백필 없이도 동작하도록 설계했다.

### 2-3. 배송방법 표기 3분화

`직배`(1,027) · `직접배송`(567) · `배송`(206) 이 같은 것으로 보인다.

- **표시는 원문 그대로** 둔다. 화면이 데이터를 고쳐 보여주면 원장과 어긋난다.
- **필터·집계만 정규화 맵**을 태운다. 맵은 `src/constants/` 에 SSOT 로 두고 주문 목록의 배송방법 필터도 같이 쓴다.
- 데이터 자체 정리(UPDATE 마이그레이션)는 **별건**이다. 어느 표기가 정본인지는 업무 판단이라 이 설계에서 정하지 않는다.

### 2-4. 합배송

`orders.consolidate_with_order_id` 로 묶인 건은 주문 목록과 **동일한 배지 로직을 재사용**한다(대표/자식 표기). 이력에서 묶음을 한 줄로 합치지 않는다 — 청구·실적은 주문 단위가 정본이고, 합치면 금액 합계가 주문 목록과 어긋난다.

## 3. 화면 설계

### 탭 구성 (`/shipments`)

```
[택배사별 실행] [준비상태] [이력]      ← 3번째 탭 신설
```

이력 탭은 **탭 진입 시 1회 마운트**한다(표가 `hidden` 이면 도구모음이 붙지 않는다 — 입고·세금계산서에서 이미 겪은 함정).

### 필터

| 컨트롤 | 기본값 | 비고 |
|---|---|---|
| 출고 기준일 from~to | **최근 1개월** | 칩으로 상시 노출(주문 목록과 동일) |
| 검색 | — | 주문번호·거래처명·품목명 (기존 orders 검색 그대로) |
| 배송방법 | 전체 | 정규화 맵 경유 |
| 거래처 | 전체 | 기존 파라미터 재사용 |

### 열

| 열 | 원본 | 숨김 가능 |
|---|---|---|
| 출고일 | `COALESCE(shipped_at, order_date)` + 대체 배지 | ○ |
| 주문번호 | `order_number` | ○ |
| 거래처 | `client_name` | ○ |
| 품목 | 대표품목 + 외 N건 | ○ |
| 배송방법 | `delivery_method` (원문) | ○ |
| 납기일 | `delivery_date` | ○ |
| 금액 | `final_amount` | ○ |
| 회계반영 | `billing_status` | ○ |

### 합계 바

`건수 · 수량 · 공급가 · 부가세 · 합계` — 주문 목록과 같은 산식(이미 구현된 `summary` 재사용). **조회조건 전체 기준**이며 현재 페이지 합이 아니다.

### 재사용 자산 (추가 구현 없음)

`ds-cond` 칩 · `ds-summary` 합계 바 · `dsListToolbar`(프리셋·열 선택·페이지당 건수) · `ordRenderSummary` 계열 렌더러.

## 7. 판단 보류 (구현 전 확인 필요)

1. **출고 이력에 `CANCELLED` 이후 복구분·반품을 어떻게 표시할지** — 현재 반품은 클레임 쪽에서 AR 조정으로만 처리된다. 이력에서 "나갔다 되돌아온 건"을 보여줄지.
2. **배송방법 정본 표기** — `직배`/`직접배송`/`배송` 중 무엇으로 통일할지(데이터 정리 별건의 전제).
3. **이력 탭 기본 기간** — 최근 1개월로 잡았으나, 출고 이력은 분기·연 단위로 되짚는 일이 많으면 3개월이 나을 수 있다.
