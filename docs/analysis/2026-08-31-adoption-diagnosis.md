# MES 도입 진단 인터뷰 — 진행 기록 (2026-08-31 개시)

> 목적: 「MES를 어떻게 도입하나」 이전에 **회사가 지금 어떤 상태인가**를 확정한다.
> 방식: 용준님 문답 누적. 라운드마다 이 파일에 답과 그 답이 계획을 어떻게 바꾸는지 기록.
> 산출물: 이 진단 위에 다시 세운 도입 계획(현 로드맵 아티팩트 갱신).

## 라운드 기록

### R1 — L1 사실 확인 (진행 중)

**R1 답변 (2026-08-31)**

| # | 질문 | 답 |
|---|---|---|
| 1 | 8/10 중단 사유 | **용준님의 보류 판단** — "실질적 테스트 이후 아직 사용하기 이르다" |
| 2 | 이카운트 실사용자 | **사내 PC 쓰는 전원** — 디자이너·영업부·현장 담당자 일부·경리부 |
| 3 | 옮겨적기 시간 | 들쭉날쭉, **월말에 몰림** |
| 4 | PC 앞에 앉는 직원 | **11~20명** |

**★R1이 뒤집은 전제 2개**

1. **8/10 중단은 거절도 배포 문제도 아니었다 — 공급자(용준님)의 품질 판단이었다.**
   → 「챔피언 복귀」 공정은 무효. 진짜 질문은 "무엇이 부족해서 보류했나"이고, 그건 사람 문제가 아니라 **완성도 문제**다.
   → 8월 재판정의 "원인은 배포(축4 수동)"도 부분 원인일 뿐 주원인이 아니었다.

2. **직원들은 시스템을 안 쓰는 게 아니라 이미 다른 ERP를 쓰고 있다.**
   → MES 계정 0·로그인 0은 "IT 미숙"이 아니라 **"이카운트로 이미 되고 있음"**의 결과.
   → 도입 = 신규 정착이 아니라 **대체(migration)**. 트리아지 「동선」 칸의 정답이 전부 바뀐다 —
     빈 동선에 밀어 넣는 게 아니라, **차 있는 동선에서 갈아끼우는** 문제.
   → 「생산현장 개인 로그인 금지」 전제도 재검토 대상(현장 담당자 일부가 이미 이카운트에 로그인한다).

### R2 — 이카운트 실태 + 보류 사유 (진행 중)

**R2 답변 (2026-08-31)**

| # | 질문 | 답 |
|---|---|---|
| 1 | 패널 보류 사유 | **3개 전부** — 결과물 품질 실무기준 미달 · 예외 케이스 오류 · 앞뒤 연결 끊김(반쪽) |
| 2 | 이카운트 입력 범위 | **주문·판매 전표 + 발주·매입 전표** (조회만이 아니다) |
| 3 | MES 착수 이유 | **4개 전부** — 3법인 통합 불가 · 원가/마진 불가 · 생산현장 부재 · 우리 방식 불일치 |
| 4 | 이카운트 연 비용 | **100만원 미만** |

**★R2가 뒤집은 것 — 종착점(공정 05 「이카운트 해지」)이 무효**

- 연 100만원 미만이면 **해지 편익은 노이즈**다. 3개월 대사 오차 0을 관문으로 걸고 해지까지 가는 설계는 비용 대비 무의미.
- 진짜로 원하는 건 해지가 아니라 **이카운트가 못 하는 4가지**(법인통합·원가마진·생산현장·자사규칙). 이 4가지는 **이카운트를 끄지 않고도** 얻을 수 있다.

**★구조적 발견 — 이중입력은 사람 문제가 아니라 API 구멍이다**

- 이카운트 오픈API: **영업(견적·주문·판매)은 입력 3종뿐, 조회 없음**. 조회는 발주서·품목·재고만.
  → 직원이 이카운트에 넣은 판매 전표를 **MES가 읽을 방법이 원리적으로 없다**(엑셀 수동 내보내기가 유일).
- 반대 방향 `POST /OAPI/V2/SaleOrder/SaveSaleOrder` 는 **완전히 열려 있고 무과금**(시간당 6,000·일 10,000).
- ⇒ **정답 구조 = 입력의 앞단만 MES로 옮기고 이카운트로 밀어낸다.** 이중입력 0.
  직원은 잃는 게 없다("이카운트에 자동으로 들어갑니다") → 저항의 소재가 사라진다.
  정본 근거 = memory `reference-ecount-openapi`(2026-08-13 실측, 동일 결론에 이미 도달해 있었음).

**★패널 보류 사유 재해석**

- 3개 전부 = **완성도 문제이지 채택 문제가 아니다.** 「챔피언 복귀·관찰 90분」은 여기에 답하지 못한다.
- 앞선 로드맵 공정 01은 폐기하고 **「미완성 3개를 닫는다」**(용준님 코드 작업)로 대체해야 한다.
- 단, 「앞뒤 연결 끊김」은 이미 원인이 특정돼 있다 — 출력완료 매칭 0%(8월 print_events 5,554건 중 0건, 작업파일 962건에 주문코드 0). 흐름이 가공→주문서라 키를 **흡수 시점에** 붙여야 하고, intake 파일명≠RIP 파일명이라 **패널 「작업폴더 내보내기」가 유일한 연결점**.

### R3 — 구조 검증 + 규모 (진행 중)

**R3 답변 (2026-08-31)**

| # | 질문 | 답 |
|---|---|---|
| 1 | MES→이카운트 밀어내기 | **이미 시도했는데 막혔다** ← 막힌 지점 미확인, R4에서 규명 |
| 2 | 이카운트 존치 | **남기는 것 지양** — 「완벽한 대체가 가능한 형태」를 원함 |
| 3 | 판매전표 입력 규모 | **4~6명 / 하루 수십~백 건** |
| 4 | 패널 우선순위 | **셋 다 닫혀야 의미** (부분 개선 무의미) |

**★목표 재정의 — 해지는 목표가 맞다. 다만 이유가 비용이 아니다**

- R2에서 「연 100만원 미만 = 해지 편익 노이즈」로 판단했으나, 용준님이 원하는 건 **정본 일원화**다.
  ⇒ 목표선 = 비용 절감이 아니라 **이중관리 제거**. 관문 설계도 「비용 회수」가 아니라 「대체 완결성」으로 잡아야 한다.
- 따라서 밀어내기(`SaveSaleOrder`) 구조는 **최종 목표가 아니라 전환기 안전장치**로만 의미가 있다 —
  전환 중 이중입력을 0으로 만들어 직원 저항을 없애고, 대체가 끝나면 함께 걷어낸다.

**★실측 — 밀어내기는 코드로 존재한 적이 없다**

- `grep -rn "SaveSaleOrder|InsertSales|OAPI" src/ scripts/` = **0건**. 이카운트 관련 코드는 전부 *가져오기* 방향(`ecount-order-import.py`·`convert_ecount_clients.py`·`migration.ts`)뿐.
- 「시도했는데 막혔다」의 대상이 ⓐAPI 인증키·Zone ⓑ전표 필수필드 ⓒ거래처·품목 코드 매칭 ⓓ실은 엑셀 내보내기 자동화(→ `feedback-ecount-chrome-export`: 팝업차단·다중브라우저·새탭 세션끊김) 중 무엇인지 **미확정**.
- ⚠️이 답에 따라 대체 경로 전체가 갈린다. R4 최우선 문항.

### R4 — 막힌 지점 규명 + 대체 합격선 (진행 중)

**R4 답변 (2026-08-31)**

| # | 질문 | 답 |
|---|---|---|
| 1 | 막힌 지점 | **전표 필수항목·형식** (인증키·Zone·코드매칭이 아니다) |
| 2 | 대체 합격선 | ①세금계산서 발행이 MES에서 ②직원이 불편 없이 입력 ③과거 데이터가 다 넘어온다 |
| 3 | 세무사·WEHAGO | **계산서·통장만 본다** |
| 4 | 전환 방식 | **병행 후 숫자가 맞으면 끈다** |

**★★ 최대 발견 — 이카운트 해지에 세무 장벽이 없다**

- 세무사가 계산서·통장만 본다면 이카운트의 **장부·재무제표 기능은 대체 대상이 아니다**.
  계산서 = 바로빌(연동 보유) · 통장 = 바로빌 수집(cron 06:00) → **둘 다 이미 이카운트 밖에 있다.**
- ⇒ 「복식부기·재무제표는 만들지 않는다」는 기존 방침과 해지가 **충돌하지 않는다**. 목표선을 낮출 필요가 없었다.
- ⇒ 남은 관문은 정확히 **3개뿐**이고 전부 사내 문제다.

**★「막혔다」= 근본 장벽이 아니라 미완 작업**

- 전표 필수항목·형식 문제 = 필드 매핑. `SaveSaleOrder` 는 `SaleOrderList[BulkDatas]`·`UPLOAD_SER_NO` 동일값=한 전표·`IO_DATE`/`CUST`/`CUST_DES`/`EMP_CD` 구조가 이미 파악돼 있다(memory `reference-ecount-openapi`).
- 다만 **최종 목표가 완전 대체**이므로 밀어내기는 전환기 안전장치로만 쓴다 —
  전환 방식이 「병행 후 대조」이니, 병행 기간의 **이중입력을 0으로 만드는 도구**로서 가치가 있다.
  (직원은 MES에만 입력 → 이카운트 전표는 자동 생성 → 대조는 시스템이 → 맞으면 끈다)

**★3개 관문의 현재 상태**

| 관문 | 상태 | 다음 |
|---|---|---|
| ① MES에서 세금계산서 발행 | 바로빌 연동 보유 · **발행누락 방지 프로젝트 중단(P1 유실)** | 재개 판단 |
| ② 직원이 불편 없이 입력 | **최대 관문** · 4~6명 × 하루 수십~백 건 · MES 주문서 실사용 이력 없음 | 입력 UX 실측 |
| ③ 과거 데이터 이관 | **Phase 0 완료**(3중 교차검증 오차 0·커버리지 100%) · Phase 1 승인 대기 | 세부점검 4종 |

### R5 — 업무 흐름 + 입력 UX 실측 (진행 중)

**R5 답변 (2026-08-31)**

| # | 질문 | 답 |

| 2 | 전표 1건 입력 시간 | ★질문이 틀렸다 — 아래 참조 |
| 3 | MES 주문서 시연 | **보여준 적이 없다** |
| 4 | 이관 범위 | **최근 2~3년** |

> R5-2 원문: "판매전표 입력 전에 ai·eps 파일을 가공하고 단가 및 후가공 등을 설정해서 단가를 측정함.
> 그러한 계산이 시간이 오래 걸리고, 디자인 작업이 완료된 이후에 메일이나 웹하드를 확인해서
> 나머지 부분을 채우기 때문에 꽤나 시간이 소요됨"

**★★★ 진단의 축이 바뀌는 지점 — 병목은 입력이 아니라 「값을 만드는 과정」이다**

- 지금까지의 모든 계획이 **「입력 화면을 어떻게 쓰게 하나」**를 풀고 있었다. 틀린 문제였다.
  실제 소요는 전표 입력이 아니라 그 **앞**에 있다: 파일 가공 → 후가공 설정 → **단가 측정** → 디자인 완료 대기 → 메일·웹하드 재확인 → 나머지 채움.
- **이카운트는 이 과정을 원리적으로 도울 수 없다 — 파일을 모르기 때문이다.**
  ⇒ 대체의 무기는 "입력이 더 빠르다"(이길 수 없다)가 아니라 **"입력할 값을 시스템이 이미 알고 있다"**(이길 수밖에 없다).
- ⇒ MES가 이카운트를 이기는 유일한 지점이 여기고, **필요한 조각은 전부 이미 설계돼 있다**:
  - 파일 규격 자동판독(`design-file-dimension-probe` — 설계 확정 **미구현**)
  - 청구면적 산식(`orderLineAmount.ts` 정본·게이트 `test:orderline` **보유**)
  - 후가공 표기·단가(`utils/finishingLabel` 쌍 **보유**)
  - 가공대기함 → 주문서 프리필(`design-tray-bundle-prefill` **보유**)
- **그런데 그 축이 끊겨 있다.** 패널 「앞뒤 연결 끊김=반쪽」(R2) · 출력완료 매칭 **0%** · 파일→주문서 백테스트 성립 90.7%(미배선). **전부 같은 하나의 축이다.**

**★「직원이 안 쓴다」는 판정은 성립한 적이 없다**

- MES 주문서를 직원에게 **보여준 적이 없다.** 계정 0·로그인 0은 거절의 결과가 아니라 **제안 부재의 결과**다.
- 패널 중단도 용준님 보류 판단(R1). ⇒ **지금까지 MES는 단 한 번도 직원 앞에 선 적이 없다.**
  「채택 계기판·관찰 90분·챔피언」 같은 채택 장치는 **아직 이르다** — 잴 것이 없다.

**★계획 재구성 방향 (R6 이후 확정)**

1순위가 「계기판」도 「챔피언 복귀」도 아니라 **「파일 1개를 떨어뜨리면 주문서 라인이 선다」**로 바뀔 가능성이 높다.
그게 서면 ①직원 입력 관문이 저절로 넘어가고(이카운트보다 빠름) ②패널 반쪽이 닫히고 ③출력완료 매칭이 붙는다.

| 3 | 우회수단 | **암산·계산기·수첩** + 이카운트 단가 호출 + **과거 거래 찾아보기** |

**★「반쪽」의 정체 — 패널이 가공만 하고 값을 안 준다**

**★순서가 결정됐다 — 관문③(이관)이 관문②(입력)를 푸는 열쇠**

> 제대로된 단가로 판매를 하고 있는건지 유지가 가능한 상황인지 제대로 판단이 되지 않음"

  네스팅·판짜기 엔진 보유(maxrects·실루엣/사각·재단 패널) → 원단 사용량을 **추정이 아니라 산출**할 수 있다.
- 장비 시간 원가의 원천도 **이미 자동 수집 중**(8월 `print_events` 5,167 · LogWatcher duration).
- ⇒ 라인별 실원가 = 재료(판짜기 산출 로스 포함) + 후가공/외주 + 장비시간. 여기서 **마진과 바닥선**이 나온다.
- ⚠️인건비 배부는 마지막에 — 근태(CAPS)는 있으나 주문 단위 귀속 근거가 없다. **추정 배부는 오히려 판단을 흐린다.**

| 로스·원가를 모른다 | 파일 → 판짜기 → 사용량 축이 끊겨 있다 |
| 숙련도 낮아 품질 문제 | 규격·판짜기·단가를 **사람 판단**에 맡기고 있다 |
| 단가 경쟁에 밀린다 | **바닥선(floor price)** 을 모른다 |

⇒ R6의 축(파일→규격→단가)에 **원가·로스**를 붙이면 셋이 동시에 풀린다. 이게 계획의 단일 중심축이다.

### R11 — 로스·판짜기·바닥선 (진행 중)

**R11 답변 (2026-09-01)**

| # | 질문 | 답 |
|---|---|---|
| 1 | 로스율 산정 | **안 잡는다** |
| 2 | 판짜기 | 기본은 **일러에서 사람이 손으로** · 현장에서 간혹 네스팅 |
| 3 | 견적 바닥선 | **경쟁사 가격을 보고** |
| 4 | 재작업·불량 | **거의 매일** |

**★★★ 가장 무거운 발견 — 원가를 모른 채 경쟁사를 따라 내려가고 있다**

- 로스율 미산정 + 바닥선=경쟁사 가격 + 매출 감소 + 단가 경쟁 심화 + 재작업 매일(비용 미기록).
- ⇒ **역마진 수주가 이미 일어나고 있을 개연성이 높고, 일어나도 보이지 않는다.**
  「나중에 보니 남지 않았다」(R10)가 사후에만 드러나는 이유가 이것이다.
- ⇒ **도입 1번은 「직원이 쓰게 하기」가 아니라 「얼마에 팔아야 하는지 알기」다.**
  R8의 「내가 먼저 쓴다」와 정확히 맞는다 — 첫 사용자도 첫 수혜자도 용준님.

**★로스 1차 근사는 판짜기 엔진 없이 선다**

- 원단 폭 W · 주문 규격 w×h → 폭방향 배치 수 = floor(W/w) → 잔폭 로스율 = 1 − (배치수×w)/W.
- 이미 있는 것: 폭/규격 원단 품목 모델 · 청구면적 산식 · 후가공 단가 · `avg_unit_cost` backfill 315품목.
- 판짜기 실측(네스팅 결과 기반 정밀 로스)은 **2단계**. 1차는 계산만으로 충분히 유의미하다.
- ⚠️단 `base_unit` 공백 129개·pack 축 혼선이 있으면 로스 계산이 **50배로 튄다**(전례 2회) → 선행 정리 필요.

**★재작업이 매일인데 숫자가 없다**

- 「재작업을 기능으로 만들지 않는다」(`docs/REWORK_RULES.md`)는 **절차 자동화**를 안 한다는 결정이지,
  **비용을 안 센다**는 결정이 아니다. 매일 발생 + 기록 0 = 원가에서 통째로 빠져 있다.
- 최소 기록 축(건수·사유·재료 재투입)만 있어도 원가와 품질 두 축에 동시에 기여한다. 숙련도 문제(R10)의 계측 수단이기도 하다.

  ⇒ 자동화가 원가·품질·가격결정에 더해 **재작업 발생 자체**를 줄인다. 편익이 넷으로 겹친다.

**★범위·정밀도가 좁게 확정됐다 — 착수 비용이 낮다**

- 상위 몇 품목 + 폭 기반 근사 ⇒ 판짜기 엔진 연동·전 품목 원가 없이 **첫 답을 낼 수 있다**.

**⚠️「당분간 혼자」= 병목 3번을 본인이 유지하는 선택**

- 존중하되 **여는 트리거를 미리 정한다**: S1 산출물이 나오고 상위 품목 마진이 확정되면 **부서 실질 책임자에게 자기 영역 숫자만** 연다.
  근거: 조직에 실질 책임자가 이미 있다(R8) ⇒ 「내가 없어도 돌아간다」(R7 목적 1번)의 발판이 조직엔 있는데 시스템만 모른다.

## 진단 종합 (12라운드 48문항 · 2026-09-01 마감)

1. **MES는 채택에 실패한 적이 없다 — 직원 앞에 선 적이 없다.** 주문서 미시연 · 패널 중단은 본인 보류 판단.
2. **병목은 입력이 아니라 값을 만드는 과정**(파일→규격→후가공→단가). 하루 수십 회, 가공자와 산출자가 동일인.
3. **이카운트는 이 과정을 원리적으로 못 돕는다**(파일을 모른다) → MES의 유일한 승부처이자 대체 논거.
4. **가장 무거운 것: 원가·로스를 모른 채 경쟁사 가격으로 판다.** 매출 감소 · 재작업 매일 · 2027 만기와 겹친다.
5. **이카운트 대체 장벽은 3개뿐**(계산서·입력 UX·이관 2~3년)이고 **세무 장벽은 없다**(세무사는 계산서·통장만 본다).
6. **조직엔 실질 책임자가 있다**(계정만 없음) → 목적 1번의 발판은 이미 존재.
7. **개발·운영 1인이 최대 리스크** → 범위를 넓히는 제안은 그 자체로 목적에 반한다.

- 지급 이연 + 추가 대출 불가 + 금리 상승 ⇒ **중기 과제(원가·마진)보다 앞에 즉시 현금 축이 와야 한다.**
- ⇒ **미수금 회수 트랙을 S0와 동급으로 올린다.** 근거:
  - 즉시 현금이 되는 **유일한** 축이다(원가 개선은 몇 달 뒤 효과).
  - aging·여신·연체 판정 축이 **이미 구현돼 있다** → 값·배선 문제일 가능성이 높아 **개발 최소**.
  - R13의 「안 보인다·독촉할 사람 없다·관계 때문에」 중 **시스템이 푸는 건 첫 번째뿐**이지만, 그게 지금 막힌 지점이다.

**★새 인과 고리 — 지급 이연이 매입 단가를 올린다**

- 「월말마다 지급을 미룬다」(R29) ↔ 「외주 단가가 계속 오른다」(R20).
- 지급이 늦는 거래처는 단가로 보상받는다. ⇒ **자금 압박이 원가를 밀어올리는 되먹임**이 있을 수 있다.
- ⇒ 미수 회수 → 지급 정상화 → 매입 단가 협상력 회복. **원가 트랙과 자금 트랙이 연결된다.**

**★법인간 거래가 부문 손익을 흐린다 — S0의 선결 조건**

- 「상당히 많다 + 정산 기준 애매 + 손익 귀속 헷갈림」 ⇒ **간판 손익이 안 나오는 이유 중 하나가 여기다.**
- ⇒ S0에서 **법인간 거래를 걷어내고** 봐야 진짜 숫자가 나온다. 관련 축은 이미 있다(법인간 원장 이관·분할청구).
- ⚠️정산 기준(마크업 정책)이 주문 단위로 갈려 있던 전례가 있다 — **기준을 먼저 확인하고 집계한다.**

**★숙련도 저하의 기원 — 사고 후 물갈이**

- 「1~2년 전 사고 이후 한 번 싹 물갈이」 ⇒ 현재 숙련도 저하는 **지속적 이직이 아니라 일회성 단절**의 결과.
- ⇒ 시간이 일부 해결하지만 **표준이 없으면 회복이 느리다**. S2의 부산물(화면=절차)이 여기에 기여한다.
- ⚠️간판도 같은 사고로 한 번 접혔다(R25) — **사고 하나가 간판·숙련도·자금에 동시에 흔적을 남겼다.**

- 내가 「놀고 있는 장비 = 고정비 부담」으로 가정한 것이 오류. **유휴 소형기는 무해하다.**
- ⇒ 이 정정은 **UV 투자 논리를 강화**한다 — 소형기 정리로 재원을 못 만들고, **3200폭 캐파 부족이 진짜 병목**이니 증설이 답.
- ⇒ 「장비는 많은데 물량이 없다」도 재해석: **고정비 문제가 아니라 캐파 구성 문제**다.

**★★★「소량 다품종」이 판짜기·로스와 직결된다**

- 건당 수량↓ + 종류↑ ⇒ **한 판에 여러 건을 모으는 판짜기(모아찍기)의 가치가 급등**한다.
- 그런데 현재: **판짜기는 일러에서 사람이 손으로**(R11) · **로스율은 안 잡는다**(R11).
- ⇒ **소량 다품종 시대에 손으로 판을 짜면 로스가 커진다.** 원가 압박의 구조적 원인일 수 있다.
- ⇒ MES는 **네스팅 엔진을 이미 보유**(maxrects·실루엣/사각·재단 패널). S1(로스 산출)과 판짜기 자동화가 여기서 만난다.
- ★S1의 폭 기반 근사는 **단품 기준**이다. 소량 다품종이면 **여러 건을 모은 판 기준**이 실제 로스에 가깝다
  → S1 1차는 근사로 가되, **모아찍기 로스**를 2단계 목표로 명시한다.

### ② 분할 — 자동 탐색 자체가 틀렸다

용준님: 「분할은 주문서에서 직접 선택을 하는 형태임. **원단 자체의 금액이 달라 청구하는 단가가 다르기 때문에**」

내가 「70cm 7분할」이라 쓴 건 **테스트 픽스처 탓**이었다 — 면적 폴백 경로를 시험하려고 후보를 700/3200 둘로 줄여
**1600 이 애초에 없었다.** 1600 을 넣으면 **1600폭 3분할(4.32㎡·2,965원)** 이 700폭 7분할(4.41㎡·3,004원)을 이긴다.

**그런데 실제 AQ2 23종으로 돌려 보니 훨씬 나쁜 게 나왔다:**

| 주문 | 종전 알고리즘 | 판정 |
|---|---|---|
| 450×90 | 900폭 무분할 · 2,259원 | ✅ |
| 450×300 | 900폭 **5분할** | ❌ |
| 600×300 | 900폭 **7분할** | ❌ |

원인 = **좁은 폭이 ㎡당 싸다**(900폭 558원/㎡ · 1800폭 634 · 3200폭 1,619) + **이음(봉제) 비용이 0**.
금액 최소화는 언제나 「잘라 이어붙여라」로 수렴한다. 봉제선은 재료비가 아니라 인건비·품질에서 비용이 나므로
**재료비 최소화로는 절대 억제되지 않는다.** 상한을 씌우는 게 아니라 **탐색을 없애야 한다.**

#### 영업의 선택은 시스템에 안 남는다 (확인)

- 판매 품목 830종은 `UV 현수막`·`수성 현수막` 처럼 **방식×매체만 있고 폭이 없다**
- `order_items` 에 원단·폭·분할 컬럼이 없다(`specification` 은 `500*90` 규격 문자열)
- `size_grade_prices`(규격등급 단가) 테이블은 **0행**

⇒ 청구 단가만 `unit_price` 에 숫자로 들어오고 **그 단가를 만든 원단 선택은 사라진다.**
용준님 결정 = **「지금은 자동선택 수정만」** (원단 선택 필드 추가는 별도 트랙).

#### 새 규칙

1. **원단 폭 안에 통으로 들어가는 조합만 후보.** 방향(가로↔세로)은 그대로 본다 — 두 변이 모두 폭 이하면 **긴 쪽을 폭**으로 둬야 소요가 적다.
2. 어느 원단에도 안 들어갈 때만 **최대 폭 1종으로, 분할 수 최소**로 나눈다 → `fitted=false` (추정 표시용).
3. 기준은 여전히 **금액**(후보 전부 단가 있음) 또는 **면적**(하나라도 없음). 섞지 않는다.

**폴백 발생률 실측**(2026 라인, 짧은 변 > 3200mm): 수성 654/7,306(9.0%) · 솔벤 98/3,042 · UV 15/1,579 · 전사 12/2,357.
= 실제로 이어붙일 수밖에 없는 구간이다. AQ-BANNER 는 BOM 에 **폭 20종(300~3200)** 이 걸려 있어 나머지는 무분할로 덮인다.
