### 결론부터 — 스위칭 기능은 필요 없다
필요한 곳엔 **이미 있고 잘 동작한다**: 재고 조정·창고 이동은 롤/M 드롭다운 + 실시간 환산 힌트(`2롤 → = 100 M`), 실사는 두 칸(`[롤 수] × [롤당 길이]`, 2×50=100M 저장 실측), 수동 발주요청·발주서는 품목의 관리단위(롤)와 롤당 단가가 자동으로 붙는다. 입고는 `수량 × pack_size` 로 base 에 쌓는다.
**발주 계열에 스위칭을 넣으면 안 된다** — 공급처와 거래하는 단위는 롤이고, 선택지를 주면 발주서·입고·단가 축이 다시 갈린다. 이번 사고가 정확히 그 갈림에서 났다.

### 실제로 틀렸던 것 — 창고별 자동 발주요청
발주·입고 계통 전체가 관리단위 축인데 **자동 생성만 base 축**으로 수량을 넣었다. 로컬에서 끝까지 돌려 실증:
```
트로피칼 재고 520M(10.4롤) · pack 50 · 안전 600M
→ [부족 품목 발주요청]  부족 80M
→ 확인창 "트로피칼 80 롤"        ← 80 은 M 인데 롤로 표기
→ 발주서 80 롤 @ 2,325
→ 입고 80 접수 → 재고 520M → 4,520M   (+4,000M · 실제 필요 80M 의 50배)
→ 부수: 입고가 발주 단가로 items.base_price 를 갱신 → 115,000 → 2,325 오염
```
정정 후: **「트로피칼 2 롤 (부족 80M)」 → 입고 2 → 520M → 620M** · `base_price` 115,000 유지.

⚠️**전날(08-26) 예상단가를 `avg_unit_cost`(base 축)로 바꾼 것은 방향이 틀렸다.** 수량(base)과 짝은 맞았지만 발주·입고가 관리단위 축이라, **수량을 포장 단위로 올림**하고 단가를 롤당으로 두는 것이 맞다. AQ 계열은 여기서도 제외(`base_unit` 없음, `pack_size=130`=실사 편의 계수).

### 같이 잡은 표기 2건

## 2026-08-27 단위 축 전수조사 — 입고가 현수막 원단을 130배로 쌓고 있었다 (prod 배포 `ca463176`)

### 조사 방법

### ① `base_price` 는 발주 단가가 아니었다

### ② 그 옆에서 나온 것 — 입고 환산이 `base_unit` 을 안 본다
`po-receive.ts:155` 이 `pack_size > 0 ? pack_size : 1` 로 **무조건** 환산한다.

| 무리 | unit | base_unit | pack | 입고 1단위 | 환산 |
|---|---|---|---|---|---|

| 현수막 AQ* | yd | (없음) | 130 | 재고 +1yd | **X** |

→ `unitConvert.packFactor()` 를 정본으로 두고 `toBase`/`fromBase`/`UOM_JS` 쌍까지 전부 경유시켰다.

**로컬 실증**(실제 엔드포인트, 픽스처 2건):
