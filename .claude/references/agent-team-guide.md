# 작업 위임 전략 가이드 (2026-06-05 개정 · 2026-07-02 모델 오버라이드 3단 · 2026-07-27 Opus 5 · 2026-08-11 공식 스펙 대조)

> 메인 루프 = **세션 모델** (2026-07-27 현재 Opus 5 1M, 이전 Fable 5·Opus 4.8). 의사결정 1차 레버는 "어떤 모델이냐"가 아니라
> **인라인 / Explore fan-out / Workflow 오케스트레이션** 중 무엇이냐다. 위임 시에만 모델 티어를 2차 레버로 쓴다(아래 3단 기준).
> **모델명은 이 문단 한 곳에만 기록** — 다른 문서·SKILL은 "세션 모델"로만 지칭(모델 교체 시 갱신 지점 1곳).
>
> ⚠️ 고정 **티어 배정은 폐기**: SKILL.md에 `model:` 필드가 하나도
> 없어 실효가 없었고(전부 메인 모델로 실행됨), 메인이 최상위 티어인 지금 "최상위는 PM 전용·개별
> 작업 금지"는 자기모순이었음. 커스텀 subagent(`.claude/agents/`)도 0개 — 빌트인만 존재.

> **정본 = 공식 문서** (2026-08-11 실측 대조): [skills](https://code.claude.com/docs/en/skills.md) ·
> [sub-agents](https://code.claude.com/docs/en/sub-agents.md) · [agent-teams](https://code.claude.com/docs/en/agent-teams.md).
> 이 문서에 스펙 값을 **복사해 두지 않는다** — 필드표는 바뀐다. 대신 **게이트가 검사한다**: `npm run audit:skills`
> (`scripts/skill-audit.cjs`, 공식 필드 목록·한도를 코드에 박아두고 P1 시 exit 1).
> 아래는 "스펙 나열"이 아니라 **이 프로젝트가 어떤 선택을 했고 왜인지**만 적는다.

## 기본 원칙: 추론 → 확인 → 실행

```
사용자 요청
  ↓
[추론] 요청의 비즈니스 맥락·진짜 목적·연쇄 영향 파악
  ↓
[확인] "제가 이해한 바" 요약 → 사용자 확인
  ↓
[설계] 신규/구조변경 → brainstorming 스킬 실행
  ↓
[실행] 인라인 처리 or 위임(Explore/Workflow)
```

대부분의 작업은 **인라인(메인 루프 직접 처리)** 으로 충분. 메인 모델은 단일 컨텍스트에서
다중 파일 분석·디버깅·리뷰를 직접 수행할 수 있다. 위임은 아래 기준에 해당할 때만.

## 위임 모드 선택

| 모드 | 언제 | 어떻게 |
|------|------|--------|
| **인라인 (기본)** | 단일~수 파일 수정, 분석, 디버깅, 리뷰 — 대부분의 작업 | 메인 루프가 직접 |
| **Explore fan-out** | 여러 디렉토리·네이밍 컨벤션을 넓게 훑어 **결론만** 필요할 때 (코드 위치·패턴 탐색) | `Agent(subagent_type:"Explore")` 1~N개 병렬. 읽기 전용, 파일 덤프 대신 결론만 회수 |
| **Plan** | 착수 전 구현 전략·영향 범위·트레이드오프를 설계해야 할 때 | `Agent(subagent_type:"Plan")` |
| **Workflow 오케스트레이션** | 4+ 파일 교차 변경, 전수 감사/마이그레이션 스윕, 다중 관점 검증을 **결정론적**으로 돌려야 할 때 | `Workflow` — ⚠️ **사용자 opt-in 필수** ("workflow" 키워드 또는 명시 요청이 있을 때만) |
| **Agent Teams** | 에이전트끼리 **대화가 필요할 때**(경쟁 가설 디버깅, 상호 리뷰). 결과만 회수하면 되는 일엔 과함 | 공식 권장 **3~5명**, 그 이상은 조율 비용이 이득을 잠식. 팀원마다 독립 컨텍스트 = 토큰 선형 증가 |

> - **모델 오버라이드 3단 기준 (2026-07-02)** — 위임 시 `model:` 파라미터로 명시.
>   ⚠️ 이 3단 배분은 **공식 권고가 아니라 이 프로젝트 관례**다(공식은 `model:` 필드 존재만 규정).
>   | 티어 | 대상 작업 | 예 |
>   |------|----------|-----|
>   | **메인 상속(기본, 생략)** | 설계·리뷰·적대적 검증·entity 격리 판단 등 품질 민감 구간 | Plan, 버그 verify, 보안 감사 |
>   | **`model:"sonnet"`** | 판단 낮은 기계적 스테이지 — 전수 grep 스윕, 경로/명칭 치환, 표 정비, 정형 구현 | Explore fan-out 스윕, Workflow 기계적 변환 스테이지 |
>   | **`model:"haiku"`** | 대량 단순 읽기·수집 — 파일 존재/헤더 확인, 카운트 집계 | 수백 파일 헤더 스캔 |
> - **모델을 바꾸기 전에 `effort` 를 먼저 본다**(`low`~`max`). 같은 모델로 사고량만 줄이는 게 더 싸고
>   품질 저하가 예측 가능하다. 기계적 스테이지 = `effort:"low"`.
> - 4+ 파일 동시 변경으로 충돌 위험이 있으면 worktree 격리(`isolation:"worktree"`) 고려.
> - ⚠️ **서브에이전트는 기본이 백그라운드 실행**이고, 백그라운드는 **포그라운드보다 좁은 툴셋**을 받는다.
>   즉시 결과가 필요하면 `run_in_background:false`. 결과가 안 오는데 툴이 없어서인 경우가 있다.

### ⚠️ 과다 위임 억제 (Opus 5 이후, 2026-07-27)

세션 모델이 Opus 5 계열로 올라오면서 **subagent를 이전보다 적극적으로 부르는 성향**이 생겼다.
이 프로젝트의 "인라인 우선" 원칙(아래 §커스텀 subagent를 두지 않는 이유)과 정면으로 부딪히므로 명시적으로 억제한다:

- **직접 몇 번의 도구 호출로 끝나는 일은 위임하지 않는다** — 파일 몇 개 읽기, 소수 편집, 단순 검색, 가벼운 검증.
- **검증·재확인 목적의 subagent 금지** — 검증은 메인 루프에서 수행(`npm run verify`·entity 감사·스모크).
- 위임은 **독립·병렬 가능하고 규모가 있는 트랙**에만 — 광범위 다중 파일 조사, 서로 무관한 도메인 동시 감사.
- 한 작업을 잘게 쪼개 여러 에이전트에 뿌리지 않는다. 하나로 끝나면 하나만.
- 위임했으면 **결과를 다시 직접 재현하지 않는다**(재작업 = 비용 2배).
- 사용자가 명시 요청하지 않은 이상 대규모 팬아웃 금지 — Workflow는 **opt-in 필수**(위 표 참조).

### 커스텀 subagent를 두지 않는 이유 (2026-06-05 결정 · 2026-08-11 전제 변경 기록)

`.claude/agents/` 커스텀 subagent는 **의도적으로 두지 않는다**(0개는 누락이 아니라 결정):
- 빌트인(Explore/Plan/general-purpose) + Workflow(opt-in) + skill 18개로 위임 스펙트럼이 충분.
- 라우트 수정 등 반복 위임은 도메인 맥락(CLAUDE.md·auto-memory) 의존도가 높아, 맥락을 잃는 독립 컨텍스트 subagent보다 **인라인 처리가 유리**.
- P1의 "인라인 우선" 방향과 일관.

> ⚠️ **결정의 근거 중 하나가 무효화됐다**(2026-08-11 공식 스펙 대조). "맥락을 잃는다"는 전제로 접었는데,
> 지금 서브에이전트 frontmatter에는 `skills:`(스킬 **본문 전체**를 기동 시 주입)와 `memory:`(세션 간
> 영속 메모리)가 있다 — 맥락 손실은 더 이상 구조적 제약이 아니라 **설정 누락**이다.
> **그렇다고 지금 만들라는 뜻은 아니다.** 결정 자체(인라인 우선)는 유효하고, 바뀐 건 근거 하나뿐이다.
> 재검토 트리거는 그대로: **맥락 독립적이고 반복 빈도가 높은 작업**이 생겼을 때. 그때 "맥락 때문에 안 된다"는
> 이유는 더 못 쓴다. 후보가 생기면 `skills:` 로 도메인 불변식을 주입하는 형태를 1개만 시범 도입해 볼 것.

## 스킬 설계 규칙 (`.claude/skills/*/SKILL.md`)

스킬은 **3층으로 로드**된다. 이 구조를 모르면 "문서를 길게 쓰면 더 잘하겠지"가 정확히 반대로 작동한다.

| 층 | 무엇 | 언제 로드 | 비용 성격 |
|----|------|----------|----------|
| 1 | `name` + `description` | **항상 상주** | 스킬 수 × description 길이. 목록 예산 초과 시 **덜 쓰는 스킬의 description부터 삭제**된다(이름만 남아 자동 호출 불가) |
| 2 | SKILL.md 본문 | 호출될 때 1회, 이후 세션 내내 잔류 | 호출 1번의 대가가 세션 전체 |
| 3 | `references/` · `scripts/` | 본문이 지시할 때만 | 사실상 무료 — **길어질 지식은 전부 여기로** |

### ★압축 생존 한도 5,000토큰 (이 프로젝트가 실제로 밟은 지뢰)

자동압축이 걸리면 각 스킬은 **본문 앞 5,000토큰만** 재첨부되고, 재첨부된 스킬 전체가 **25,000토큰
공동 예산**을 최근 호출 순으로 나눠 쓴다. 즉 **긴 스킬은 압축 후 뒷부분이 조용히 사라진다** — 에러도,
경고도 없이 그냥 지시가 없어진 상태로 계속 돈다.

`auto-improve/SKILL.md` 가 정확히 이 상태였다: 8KB(2026-05-11) → **197KB·본문 515줄·~57,000토큰**(2026-08-07).
「Area 6 자기진화」가 배운 것을 SKILL.md 본문에 계속 덧붙이는 구조라 3개월간 24배로 자랐다.
**압축 후 살아남는 건 앞 9%뿐** — 누적된 교훈일수록 뒤에 붙으니 **가장 비싸게 배운 것이 가장 먼저 버려진다**.
`doc-diet-audit` 은 현황판·메모리만 봐서 스킬은 감사망 밖이었다(현황판 90K자 사고와 같은 형태의 재발).

> **누적형 지식은 SKILL.md 본문에 쓰지 않는다.** 본문은 목차·분기·안전 불변식만.
> 배운 것은 `references/<영역>.md` 로 보내고 본문에는 "언제 그 파일을 읽어야 하는지"만 남긴다.

### description = 「무엇을 한다」 + 「언제 쓴다」

자동 호출의 **유일한** 라우팅 신호다(본문은 호출 후에야 읽힌다). 빠뜨리면 본문 첫 문단으로 추론하는데 부정확하다.
- 핵심 용도를 **앞에** — 길이 상한에서 잘리는 건 뒷부분이다.
- **트리거 낱말이 겹치면 구분 문구를 넣는다.** 이 프로젝트는 「검증」6개·「배포」6개·「확인」5개·「점검」4개가
  겹친다. 겹치는 쪽에 "~는 X 스킬" 같은 배제 문구가 없으면 어디로 갈지 불안정하다.
- 사람이 타이밍을 정해야 하는 것(`/deploy`·`/db-reset-seed`)은 `disable-model-invocation: true`.
  반대로 **알고는 있되 행동으로 발동하면 안 되는 배경지식**은 `user-invocable: false` 쪽이다 — 둘은 다르다.

### 안 쓰고 있는 레버 (전 18개 스킬이 `name`+`description`만 사용 중)

| 필드 | 쓸 자리 |
|------|--------|
| `context: fork` + `agent:` | 결과만 필요한 무거운 읽기 스킬(`auto-scan`·`qa-audit`·`security-audit`·`entity-audit`)을 **격리 컨텍스트에서 돌리고 결론만 회수**. 임기응변 위임과 달리 **선언적**이라 "과다 위임 억제" 원칙과 충돌하지 않는다 |
| `allowed-tools` | 그 턴에 한해 승인 없이 쓸 툴 지정(다음 메시지에 자동 해제) |
| `argument-hint` | `/ship` 처럼 인자를 받는 스킬의 자동완성 힌트 |
| `paths` | 특정 파일을 만질 때만 활성(예: UI 스킬을 `src/pages/**` 로 한정) |
| `model` · `effort` | 기계적 스킬을 낮은 티어/사고량으로 |

### 게이트

```bash

```
frontmatter 유효성(공식 필드표 대조·오타 키 검출)·본문 500줄·압축 생존 한도·description 상한·
서브에이전트 name 중복·트리거 낱말 충돌을 본다. **스킬을 고친 뒤 이걸 안 돌리면 조용히 잘린 채로 돈다.**

## Workflow 패턴 (다중 에이전트, opt-in 시)

사용자가 워크플로우를 명시 요청했을 때 활용. 흔한 단일 페이즈 패턴:

- **Understand** — 서브시스템별 병렬 reader → 구조 맵 종합
- **Review** — 차원별(버그/보안/성능/entity격리) find → 발견마다 적대적 verify (pipeline)
- **Migrate/Audit** — 대상 사이트 discover → 각 변환(worktree 격리) → 검증
- **Research** — 다각도 web 검색 sweep → deep-read → 인용 종합

> 기본은 `pipeline()`(스테이지 간 배리어 없음). 전체 결과를 모아야 할 때만 `parallel()` 배리어.

## subagent/Workflow dispatch 필수 포함 사항

라우트 수정을 위임할 때 프롬프트에 반드시 포함 (도메인 불변식 — 모델 무관하게 유효):

```
공통:
- "목록(GET /) + stats + count + summary + badge 엔드포인트 모두 수정"
- "INSERT 시 entity_id: getEntityId(c) 포함"
- "0이 유효값인 필드에 || default 금지, ?? default 사용"
- "escapeHtml/fmtMoneyInput 등 전역 함수 사용, 로컬 정의 금지"
- "회사 정보 → getEntityCompanyInfo(db, entityId), 팝빌 → getEntityCorpNum(db, entityId)"
- "완료 후 npm run typecheck 실행"

품목/재고 관련:
- "품목 조회 시 print_methods/print_media LEFT JOIN 포함 여부 확인"
- "품목 필터는 item_type (PRODUCT/GOODS/MATERIAL) 기반, is_sales_item 의존 금지"
- "GOODS 등록 시 is_sales_item=1, is_purchase_item=1 동시 설정"
- "재고 변동 시 inventory_transactions 기록 여부 확인"
- "SHEET 품목은 order_items.selected_material_id 확인"
```

## 설계 계약서 (Design Contract)

- **소형** (1 파일, 버그 수정): 불필요
- **중형** (2~3 파일): 인라인 계약 (dispatch prompt에 스키마+응답포맷+필드명 포함)
- **대형** (4+ 파일): 정식 계약서 (DB 스키마 SQL + API 인터페이스 JSON + 프론트 필드명 + 파일 목록)
  → Workflow 사용 시 schema 옵션으로 구조화 출력 강제 권장

## 통합 검증
